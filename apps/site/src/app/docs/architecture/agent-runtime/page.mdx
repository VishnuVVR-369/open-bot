# Agent runtime

Teammates are powered by Codex, OpenAI's coding agent.
One `codex app-server` process on the computer serves every teammate's conversations.
The worker drives it remotely over JSON-RPC, adds open-bot's own tools, and turns its stream of events into the chat timeline.

## Why Codex, and why on the computer

The teammates use `gpt-6.1-sol` on a ChatGPT subscription.
On a subscription, the model is only reachable through Codex, not through an API key.
Codex's shell and file tools act on the machine Codex runs on, so that machine has to be the computer.

This also gives teammates a capable agent loop for free: planning, a shell with streaming output, file patches, web search and context compaction.
open-bot adds what Codex doesn't have: a desktop, approvals, schedules, memory, teamwork and the rest, as **dynamic tools**.

## The connection

```text
worker ── ws://botd:7000/codex?token=… ──▶ botd ── ws://127.0.0.1:4500 ──▶ codex app-server
```

`CodexManager` (`apps/worker/src/codex/client.ts`) keeps one connection for the whole worker.
botd bridges it byte for byte to the app-server, which only listens on localhost.

`@open-bot/agent` holds the client:

- `CodexClient` speaks JSON-RPC 2.0 over the websocket. It sends `initialize` (with `experimentalApi: true`) and `initialized`, then matches responses to requests by id, with a 120-second timeout per request.
- Messages with a method and an id are **server requests**, which Codex sends when it needs an answer: a tool call, an approval, a token refresh. The client passes them to a handler and sends back its result or a JSON-RPC error.
- Messages with only a method are **notifications**, like streamed text.
- `src/protocol/` holds the protocol types, generated from the pinned Codex version with `pnpm --filter @open-bot/agent generate:protocol` (`codex app-server generate-ts`). The `Methods` map in `client.ts` types the methods open-bot calls, so a protocol change shows up as a type error.

`CodexManager` then:

- reconnects 3 seconds after a drop, and fails every run in flight with "Lost the connection to the computer";
- signs in on every connection (see [Models and usage](/docs/flows/models-and-usage#signing-in-to-chatgpt));
- routes notifications and server requests to the session that owns the thread, by `threadId`;
- tracks which threads are loaded in the app-server since the last reconnect;
- declines approvals and tool calls for threads no session owns, so a stray request never hangs.

## Methods open-bot uses

| Method                                                                                                 | Used for                                                                         |
| ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| `account/read`, `account/login/start`, `account/logout`                                                | ChatGPT sign-in, both borrowed tokens and device codes                           |
| `account/rateLimits/read`                                                                              | The plan's usage windows, shown in Settings and used to find when a limit resets |
| `thread/start`, `thread/resume`, `thread/fork`                                                         | Getting the thread for a run                                                     |
| `turn/start`, `turn/steer`, `turn/interrupt`                                                           | Running, steering and stopping a turn                                            |
| `fs/readFile`, `fs/writeFile`, `fs/readDirectory`, `fs/createDirectory`, `fs/getMetadata`, `fs/remove` | Writing workspaces and skills, and the Files page                                |
| `skills/list`, `mcpServerStatus/list`                                                                  | Checking skills and testing MCP connections                                      |

The worker never runs shell commands on the computer itself.
File access for the UI goes through Codex's `fs/*` methods, which run as the `bot` user.

## Threads

open-bot keeps one Codex thread per teammate per lane of a chat.
The conversation (`chat`) stays in `bot_threads`, with its existing unique pair.
Automation and email threads live in `chat_lane_threads`, uniquely keyed by `chat_id`, `teammate_id` and `lane`.
Keeping the old conversation key lets an older worker keep running during deployment.

Lanes are `chat`, `schedule:<id>`, `trigger:<id>`, and `inbox`.
Only runs in the same lane wait for one another. Your messages steer only the conversation lane.
Each table records the same thread metadata:

| Column              | Meaning                                                                     |
| ------------------- | --------------------------------------------------------------------------- |
| `chat_id`, `bot_id` | The pair the thread belongs to (unique)                                     |
| `codex_thread_id`   | Codex's id for the thread                                                   |
| `tools_revision`    | A hash of the tools and developer instructions it started with              |
| `memory_generation` | The teammate's memory generation when the thread was made                   |
| `auth_mode`         | `plan` or `api_key`: the model provider it was created with                 |
| `configuration_key` | A hash of the MCP servers, the `AGENTS.md` and the model route it was given |

A thread is started with:

- `cwd` set to the teammate's workspace, so Codex loads that teammate's `AGENTS.md`;
- `developerInstructions` set to the rules every teammate follows (`DEVELOPER_INSTRUCTIONS` in `apps/worker/src/instructions.ts`);
- `dynamicTools` set to every open-bot tool;
- `sandbox: "danger-full-access"` (the container is the boundary);
- `approvalPolicy` of `untrusted` for teammates that ask before everything, or `never` otherwise;
- the model provider and MCP servers as config (see below).

### Choosing a thread

A thread keeps the instructions, tools, provider and MCP servers it was created with.
So the session checks each of those before using an existing thread:

  <ThreadDecisionDiagram />
</Figure>

- **A new tool set or new developer instructions** (a different `tools_revision`) start fresh threads, because a thread can't be given new tools.
- **A new memory generation** starts a fresh thread too. A thread's history may contain facts you have since corrected or deleted, and forking it would carry them over. See [Memory](/docs/flows/memory#generations-and-stale-threads).
- **A different provider, MCP set or `AGENTS.md`** forks the thread with `thread/fork`. The fork keeps the whole conversation and gets the new provider, servers or instructions. This is how a chat moves between your ChatGPT plan and your API key mid-conversation, and how an edited profile, a new Always allow rule or a new teammate reaches chats already going.
- **A different model route** forks the thread the same way.
  A loaded thread keeps its provider's address, so turning the [model proxy](#the-model-proxy) on or off, or moving it, would otherwise leave chats talking to the old address.
  The route is left out of the hash while a thread uses Codex's default, so turning the proxy off gives back the hash from before it.
  Each chat forks once when its route changes, on the plan and on the API key alike, and the only cost is one cold prompt cache.
- **Otherwise**, a thread that is loaded is reused, and one that isn't is resumed from Codex's state on the volume with `thread/resume`.

## The model proxy

Codex on the computer sends its model requests to the worker, which forwards them to the model and logs each one.
The worker serves them at `/model-proxy/<token>/<route>/...` on its own port, next to the internal API (`apps/worker/src/features/model-logs/`).

| Route  | Path under the route | Upstream                                                             | Credential                                               |
| ------ | -------------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| `api`  | Any                  | `OPENAI_API_BASE_URL`                                                | The worker adds your API key                             |
| `plan` | `/backend-api/codex` | `https://chatgpt.com/backend-api/codex`, or `OPEN_BOT_PLAN_BASE_URL` | Codex's own ChatGPT login, passed through and never kept |

- **Addresses.** Both routes are reached as the computer reaches the worker: Railway's private address (`http://worker.railway.internal:4001`, from `RAILWAY_PRIVATE_DOMAIN` and `WORKER_PORT`), or `http://host.docker.internal:<WORKER_PORT>` for a local computer container.
  `MODEL_PROXY_URL` overrides it.
  API key threads get a provider whose `base_url` is the `api` route.
- **The plan keeps Codex's built-in provider.** Plan threads keep the `openai` provider and get `openai_base_url` set to the `plan` route, which ends in `/backend-api/codex` like ChatGPT's own.
  Codex ties its Codex backend behavior to that provider and that ending (`supports_codex_backend_routes()`): WebSockets, workspace routing, its model headers and context management.
  A custom provider would lose them.
  The proxy adds no credential on this route: Codex sends the computer's ChatGPT `Authorization` and account headers, which go to ChatGPT unchanged.
  Account and rate-limit calls go to `chatgpt_base_url`, which isn't model traffic and stays direct.
- **Pass-through.** The proxy forwards any path under the route to that route's fixed upstream, never to an address from the request.
  Request and response bytes go through unchanged as they arrive, compressed or not, and a copy is read on the side.
  Model requests (POSTs) are logged in full; the `models` list only as metadata.
- **The token.** The URL carries `HMAC(ENCRYPTION_KEY, "model-proxy")`, compared in constant time.
  A wrong token or route gets a 404.
  It keeps the rest of the private network out; it is not what lets a request spend the key.
- **The key.** The worker adds `Authorization: Bearer <key>` only to a request whose `thread-id` (or parent thread) belongs to a live run on the API key in the session registry, a run that passed the cap check.
  Anything else gets a 403 and never reaches the upstream.
  Codex is given no key at all.
- **Never blocking.** Forwarding never waits on logging: each chunk is sent on to Codex before its copy is read.
  A finished request is rebuilt (`ResponseReader` in `@open-bot/domain`) and queued in memory; the writer saves batches every second or every 100 requests.
  Reading one response has a 16 MiB budget, counted in bytes of compressed input waiting for the decompressor and characters of text: an unfinished event (each data line costs 8 more, so empty lines count), the items rebuilt so far, and the ids, errors and warnings noted along the way.
  It is checked after every chunk going into or coming out of the decompressor, so the count passes the budget by one chunk at most.
  The count is of text: parsed items take more memory than the text they came from, and the first 1 MiB of the raw response is kept besides.
  Past the budget the response is still forwarded whole, and its log keeps only the metadata, the raw start and a warning that it was too large to read.
  Only the first 10 events that aren't JSON get a warning of their own.
  Reading never throws into forwarding: a response whose copy can't be read (JSON nested too deeply to walk, say) is still forwarded whole, over HTTP or a WebSocket, and logged with a warning, and a WebSocket connection goes on to the next response.
  While the database can't be reached, a batch is retried with backoff for 5 minutes, and the queue holds at most 64 MB.
  Past either, the requests are dropped and a `model_log_gaps` row records them once the database answers again.
  When the database answers but refuses a batch, the writer saves its requests one at a time and drops only the ones it refuses, so one bad request never holds up the rest.
  See [Data](/docs/architecture/data#model-logs) for the tables.
- **Shutdown.** The HTTP server stops taking requests first, then the proxy waits up to 10 seconds for the requests still running to be logged, and only then does the writer save what is queued.
  Requests still running after that are recorded as a gap.
- **Upstream failures.** When the upstream can't be reached the proxy answers 502, and when it breaks off mid-stream the proxy breaks Codex's stream too, so Codex retries as it would on a direct connection.
- **Kill switch.** `MODEL_PROXY=off` sends plan threads straight to ChatGPT, and API key threads straight to `OPENAI_API_BASE_URL` with the key as the provider's bearer token, as before.
  The route revision forks each such thread once to change course, with no computer redeploy.

### WebSockets

On the plan, Codex speaks the Responses API over a WebSocket to `/responses`, and falls back to HTTP streaming only after a WebSocket fails; that fallback lasts for the rest of the session.
The proxy takes both, and Codex's upgrade arrives on the worker's HTTP server next to its other WebSockets (`apps/worker/src/ws.ts`).

- **The handshake.** The proxy first checks Codex's upgrade as `ws` would (the method, key, version and subprotocols), and answers 400 to one it can't complete, without opening anything upstream.
  It then opens the upstream connection, with Codex's headers minus those that belong to one hop, and answers Codex's upgrade with the upstream's headers (`x-reasoning-included`, `openai-model`, `x-codex-turn-state`).
  When the upstream refuses the upgrade (a 401, a 426 that sends Codex to HTTP, a 429 at the usage limit), Codex gets the same status and headers as soon as they arrive, so its fallback never waits on the body, and then the whole body as it streams; the log keeps its first 1 MiB.
  Codex's side of the relay is uncompressed, since it is the private network; the upstream side is compressed when Codex asked for it.
- **The relay.** Every message, ping and pong goes on as it came, text or binary, and a close goes on with its code and reason.
  When one side drops without a close, the proxy drops the other.
  A side that can't keep up pauses the other past 8 MiB waiting to go out, and resumes it under 1 MiB.
- **One request per message.** Each `response.create` is logged as one request, with `transport` `websocket` and `method` `response.create`, from the message to the end of its response (`response.completed`, `response.incomplete`, `response.failed`, or an `error` that ends it as Codex reads it).
  The thread and turn come from the message's `client_metadata`, since a connection outlives the turn it was opened in.
  Codex sends one request at a time on a connection; should a request overlap one still streaming, the model's events are read in order, oldest request first, both requests carry a parse warning, and neither is continued from.
  `codex.rate_limits` events are stored as the same rate-limit headers the plan sends over HTTP, and headers carried by events (`codex.response.metadata`, errors) join the handshake's.
- **Rebuilt input.** When a request extends the one before it on the same connection, Codex sends only the new items with a `previous_response_id`.
  The proxy keeps, per connection, the last request's full input and the items its response added once it completed, exactly as Codex does (`get_incremental_items` in Codex's `core/src/client.rs`), and stores each request with its full input rebuilt: the last full input, then the items the last response added, then the new items.
  `sent_input_from` says where the items the message sent begin, so the message itself rebuilds too.
  Blobs are stored by hash, so the shared history costs nothing.
  A `previous_response_id` that isn't the last completed response on the connection is stored as sent, with a parse warning, and the chain starts again at the next full request.
  The chain holds at most 64 MiB of text per connection.
- **The budget.** A response's messages are read under the same 16 MiB budget as an HTTP body (`WebSocketResponseReader` in `@open-bot/domain`): the events it keeps, the strings it notes and the headers events carry, checked after every message.
  Past it the response is still relayed whole, its log keeps the raw start and a warning, and the next request on the connection is stored as sent.
- **Shutdown.** Connections with no response streaming close at once with 1001, so Codex reconnects to the next worker; one with a response streaming closes with 1001 when the response ends and is logged.
  The close goes out after whatever is still queued for Codex, and shutdown waits for both sides to close, so a slow reader still gets its last response.
  Connections still open when the 10 seconds run out are dropped, and their responses recorded as a gap.

A request is linked to its run through Codex's own ids: the `x-codex-turn-metadata` header (or the same JSON in the body's `client_metadata`) carries the thread, the turn and the request's kind (`turn`, `prewarm`, `compaction` or `memory`).
They are stored as sent, and joined to runs when the logs are read, never resolved when they are written.

## The Codex event log

Every JSON-RPC message between the worker and Codex is logged, both ways, in `codex_events` (see [Data](/docs/architecture/data#codex-events-turns-and-tool-calls)).
`CodexClient` takes an observer per connection, called for each message before it is handled or after it is sent; `CodexManager` passes one from `CodexEventTap` (`apps/worker/src/features/model-logs/codex-events.ts`).
Logging never holds up a turn: the client ignores anything the observer throws, and the tap itself catches its own failures and counts them as lost.

- **What is logged.** The worker's requests and Codex's responses to them, Codex's server requests and the worker's responses, and notifications.
  Each row has its direction (`to_codex` or `from_codex`), its JSON-RPC kind, its method, its id, and the thread, turn and item it names.
  A response keeps the method of the request it answers and inherits its thread, turn and item.
- **Deltas are counted, not stored.** Streaming deltas (`item/agentMessage/delta`, `item/commandExecution/outputDelta`, any method ending in `delta`) are counted per item.
  The completed item carries all of their content, so its `item/completed` row gets the counts in `delta_counts`; counts for items that never completed go on the `turn/completed` row.
- **The run.** The worker's own requests take the run whose work sent them: `RunSession.execute()` runs inside an `AsyncLocalStorage` scope (`apps/worker/src/core/run-scope.ts`), and the connection and sign-in run outside it.
  Messages from Codex take the run that started their turn, else the live run on their thread in the session registry, else the live run that last asked about their thread, since Codex's first messages on a new thread arrive before the session knows its id.
  Messages that belong to no run (sign-in, the Files page, skills checks) keep an empty `run_id`.
- **Order.** `sequence` starts at the worker's start time in microseconds and goes up by one per logged message, so it orders messages across restarts.
- **Turns.** When `turn/start` returns, the tap adds a `run_turns` row with the run, the thread, the turn, how the run reaches the model at that moment (`plan` or `api_key`) and when the request was sent.
  A run that falls back from the plan to the API key mid-run has two.
- **Redaction.** Every payload is redacted before it is queued; see [Security](/docs/security#model-logs).
- **Never blocking.** While the connection handles a message, the tap does only constant work: the method, the ids, the run, the delta counts and the order.
  The client gives it each message's size as JSON text, measured where the frame is read or written, so nothing has to be measured again.
  The redaction runs after the connection has handled the message (`setImmediate`), and is bounded: a message past `MAX_EVENT_SIZE` (2 MiB) is never read, and a payload nested deeper than `MAX_JSON_DEPTH` (256) or holding more than `MAX_EVENT_NODES` (50,000) values is refused.
  A message waiting for its redaction holds room in the writer's queue for its size (`reserveEvent`), so waiting payloads count toward the queue's 64 MB limit like queued ones; when there is no room, its payload is never held, and it is stored as a stub, or counted as lost when even that doesn't fit.
  At shutdown, after Codex disconnects and before the writer stops, the tap redacts and queues every message still waiting (`drain()`), so a message seen just before shutdown is saved rather than arriving at a stopped writer.
  A message that isn't stored whole keeps a stub row: its method, ids, run and order, with `payload` holding only why (`omitted`) and its `size`.
  Every stub, and every message the tap failed to read, is counted in `model_log_gaps` as a lost Codex event.
  Rows go through the same writer as the model requests, with its queue limit, retries and gap rows.

## Instructions

A teammate's instructions come from three places, from most general to most specific:

1. **Developer instructions**, set once per thread. They are the same for every teammate: how the shared computer works, how to use the desktop safely, never to type passwords, how payments and emails are approved, when to use automations, swarms and teammates, how to use memory. Changing them starts fresh threads.
2. **`AGENTS.md`** in the teammate's workspace, which Codex reads because it is the working directory. The worker regenerates it from the database at the start of every run. It holds the teammate's name, role and job, its approval rules by autonomy level, its Always allow rules, its email address, its connected services, and its teammates with their jobs.
   Codex reads it when a thread starts, forks or is resumed from disk, never again while the thread is loaded, and ignores new developer instructions on a resume or fork.
   So the session hashes the file into the thread's `configuration_key`, and a change forks the thread.
3. **The prompt** of each run, built fresh (below).

```md title="/home/bot/bots/milo/AGENTS.md (abridged)"
# Milo

You are Milo, the user's travel planner.

## Your job

Find and compare flights and hotels. Prefer nonstop flights...

## Approvals

Before any consequential action, call request_approval and wait: sending or replying
to messages, posting or publishing, deleting data, and changing settings...

## Your teammates

Ask them with ask_teammate when a question falls in their job:

- Penny, personal shopper

## Memory

Saved memory is provided with each task. Use the memory tools to recall or change it.
MEMORY.md is a generated export; file edits are not saved.
```

## The prompt

Each run's text input is assembled by `RunExecutor.buildPrompt()`, in this order:

1. `[Now: Fri 31 Oct 2026, 09:14 (Europe/Lisbon)]`, in your time zone from Settings.
2. In a group chat: who else is in the chat with their jobs, and what you and the other teammates said since this teammate last spoke (up to 10 of each, 1,500 characters per line).
3. The memory packet: pinned and relevant memories, with their ids and revisions (see [Memory](/docs/flows/memory#what-a-run-sees)).
4. Your Always allow rules, so rules you add mid-conversation reach a thread that already read its `AGENTS.md`.
5. For the conversation lane, a bounded note of other lanes' completed or failed, non-quiet results that it has not heard. Results are marked delivered only after Codex accepts the turn; later turns retain the approval requirement for account data already passed on.
6. The request itself: your message, or the text the trigger produced.
7. A list of attached files with their paths, types and sizes.

Image attachments are also passed as `localImage` inputs, so the model sees them.
A `/name` in the request adds a `skill` input with the path of that skill's `SKILL.md`, so Codex loads it explicitly.

## Turns

A run is one turn, or two when it falls back from the plan to the API key mid-run, the second on a new thread.
The session calls `turn/start` with the input, the teammate's model and reasoning effort, the approval policy and the trigger.

### From Codex events to the timeline

The session maps Codex notifications to timeline items (`apps/worker/src/runs/mapper.ts`):

| Codex                      | Timeline item                                                                                 |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| `agentMessage`             | `message`, with phase `commentary` or `final`                                                 |
| `reasoning` (summary only) | `reasoning`, streamed by `summaryTextDelta`                                                   |
| `commandExecution`         | `command`, with streamed output (the last 20,000 characters are kept), exit code and duration |
| `fileChange`               | `file_change`, with each path, kind and diff                                                  |
| `turn/plan/updated`        | `plan`, with each step's status                                                               |
| `webSearch`                | `web_search`                                                                                  |
| `mcpToolCall`              | `tool`, named `server.tool`                                                                   |
| a dynamic tool call        | recorded by the tool handler itself, with richer detail (a screenshot, an approval card)      |

Text deltas are appended to their item and coalesced by `RunEventWriter`.
`thread/tokenUsage/updated` adds to the run's token counts, kept separately for the plan and the API key.

The turn ends with `turn/completed`, whose status is `completed`, `interrupted` or `failed`.
A failure carries `codexErrorInfo`, which is how the session knows the plan's usage limit was reached (`usageLimitExceeded`) or the API key was rejected (`unauthorized` or HTTP 401).

The reply you see is the last `final` message of the turn, or the last message if none is final.

### Server requests during a turn

| Request                                 | Answered by                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------------ |
| `item/tool/call`                        | `ToolHandlers`: the result of an open-bot tool                                 |
| `item/commandExecution/requestApproval` | The approval service, after Always allow rules. Returns `accept` or `decline`. |
| `item/fileChange/requestApproval`       | The same, for file changes                                                     |
| `item/tool/requestUserInput`            | Empty answers: teammates ask through their own tools instead                   |
| `mcpServer/elicitation/request`         | Declined                                                                       |
| `account/chatgptAuthTokens/refresh`     | `CodexManager`, with a fresh token from the host's login                       |

### Steering and interrupting

A message you send while the teammate is working joins the running turn with `turn/steer`, which takes the expected turn id so it can't land on the wrong turn.
Your hand-back notes after a takeover use the same path.
If the turn has already ended, a new run is queued instead.

Stopping a run calls `turn/interrupt`.

### Long waits inside tools

Codex runs dynamic tools inside a code cell that hands control back to the model after about 30 seconds, even while a tool is still waiting.
The model may then poll, or end its turn.
So open-bot never relies on a tool blocking for long:

- Approvals and takeovers wait in the tool for up to 10 minutes, and the run shows as `waiting`. A quick answer goes straight back into the turn.
- If the turn ends first, the waiter is released, and your later decision or hand-back starts a **new run** in the same chat that says what you decided.
- Emails don't wait at all: they go to an outbox and send when you approve.
