# Data and events

Postgres is the system of record, the job queue, the event log and the message bus.
This page covers the schema, how runs are queued, how events are stored and streamed, and the three `NOTIFY` channels.

### Conventions

- Primary keys are random UUIDs, except `run_events.id`, which is a `bigserial` so events have a global order.
- Timestamps are `timestamptz`.
- Structured values (attachments, timeline payloads, approval payloads) are `jsonb` with a TypeScript type attached with `$type<>()`.
- Deleting a teammate archives it (`bots.archived_at`). Rows that belong to it cascade or set null as each foreign key says.
- Secrets are never stored in plain text. `encryptSecret()` in `@open-bot/domain/server` uses AES-256-GCM with a random 12-byte IV, and stores `iv.tag.ciphertext` in base64url.
- The settings row is read only through `ownerSettings()` and `ownerTimeZone()` in `packages/db/src/settings.ts`, so a missing row means the same defaults everywhere.

### One writer per table

Every table has one owner, the one module that inserts, updates and deletes its rows, listed in `packages/db/src/owners.ts`.
Most owners are worker services; the web app changes their tables through the worker's internal API.
Any server code may read any table.
The `open-bot/table-owners` lint rule fails a write anywhere but the owner, so a rule about a table (a lock, a revision check, an event to publish) lives in one place.
A module that must change a few columns in its own transaction, like memory stopping the turns that read old memory, is listed under `shared` with those columns, and the rule lets it set only them.
`pnpm test:scripts` fails when a `shared` entry no longer writes its table, so the list only shrinks.

Advisory locks are named in `LOCKS` in `packages/db/src/locks.ts` and taken with `lockUntilCommit()`.
Their keys never change once shipped, because the web app and the worker deploy separately and must still exclude each other.

### Migrations

Migrations are generated SQL files in `packages/db/drizzle/`; `meta/_journal.json` records their authoritative order.

```sh title="Terminal"
pnpm db:generate   # write a new migration from changes to schema.ts
pnpm db:migrate    # apply pending migrations
```

`0020` runs `CREATE EXTENSION IF NOT EXISTS vector`, so the database must have pgvector available.
The local Compose file uses the `pgvector/pgvector:pg17` image.

## The run queue

A queued run is a row in `runs` with `status = 'queued'`.
Anything that wants a teammate to work calls `enqueueRun()` (`apps/worker/src/runs/queue.ts`), which:

1. inserts the run with its trigger, prompt and links (the message, schedule, trigger or parent run that caused it);
2. appends a first `status: queued` event, so the chat shows it right away;
3. sends `NOTIFY openbot_worker, 'runs'`.

The worker claims runs with `UPDATE ... FOR UPDATE SKIP LOCKED`, at most one per teammate per lane of a chat, oldest first.
The query is on the [Worker](/docs/architecture/worker#claiming-work) page.

`runs.waiting_for` says what a waiting run waits for: `approval` or `takeover`.
`runs.cancel_requested_at` marks a run you stopped, until the worker processes it.
`runs.lane` is the lane of the chat it works in (see [Threads](/docs/architecture/agent-runtime#threads)).
`runs.quiet` marks a quiet routine's run that had nothing to report; it doesn't count as activity in the chat.

## The event log

`run_events` is append-only.
Each row has the run id, the chat id (so a chat's events are one index scan), and a jsonb `payload` of one of four types:

```ts title="RunEventPayload (packages/domain/src/timeline/timeline.ts)"
type RunEventPayload =
  | { type: "status"; status: RunStatus; error?: string; waitingFor?: "approval" | "takeover" }
  | { type: "item"; item: TimelineItem } // insert or replace an item by id
  | { type: "delta"; itemId: string; delta: string } // append text to an item
  | { type: "usage"; inputTokens: number; cachedInputTokens: number; outputTokens: number };
```

A `TimelineItem` is one thing the run did, with an `id`, a `status` (`running`, `completed` or `failed`) and timestamps.
There are fourteen kinds: `message`, `reasoning`, `command`, `file_change`, `plan`, `web_search`, `tool`, `computer` (a desktop action with its screenshot), `approval`, `takeover_request`, `handoff`, `user_message` (steering and hand-back notes), `swarm` and `error`.

Items are written whole whenever they change, and the reducer replaces them by id.
Deltas only append text.
This keeps the reducer simple and makes the log easy to read in SQL.

`applyRunEvent(state, payload)` in `@open-bot/domain` folds events into a run's timeline.
It is pure and shared: the web app uses it on the server to build a chat's first snapshot, and in the browser to apply live events.

### Why a log

- **Streaming.** The stream route reads rows after a cursor, so streaming is just a query.
- **Resuming.** A tab that reconnects sends its last id and gets exactly what it missed.
- **Replay.** Every desktop action points to its screenshot in `artifacts`, so you can step through what a teammate did, frame by frame, at any later time.
- **Late updates.** An approval decided after its run ended still appends an event to that run (`appendRunEvent`), so the card in the chat updates.

## Notification channels

`packages/db/src/index.ts` defines three channels:

| Channel          | Payload                                                 | Sent by                              | Listened to by            |
| ---------------- | ------------------------------------------------------- | ------------------------------------ | ------------------------- |
| `openbot_worker` | `runs`, `schedules`, `triggers`, `accounts` or `cancel` | the web app and the worker           | the worker                |
| `openbot_chat`   | a chat id                                               | the worker, after storing run events | the web app's SSE streams |
| `openbot_app`    | a JSON `AppEvent`, like `{"type":"approvals"}`          | the web app and the worker           | the web app's SSE streams |

`AppEvent` has about twenty types, one per area of the UI: `bots`, `chats`, `approvals`, `takeovers`, `lease`, `computer`, `notification`, `schedules`, `triggers`, `tasks`, `memory`, `vault`, `purchases`, `connections`, `email`, `telegram`, `skills`, `pages`, `profile`, `lessons` and `auth`.
Each one tells open tabs which cached queries to refetch.

Notifications are hints, not data.
Every listener reads the rows itself, and the worker sweeps for queued runs and cancellations every 15 seconds, so a dropped notification only delays something.

## Accounts

Your Gmail, Google Calendar and Notion are three tables and two kinds of `connections` row.
See [Your accounts](/docs/flows/accounts) for what you see.

- An **`accounts`** row is one sign-in: Google's `sub`, or Notion's workspace and user, unique per provider, with the granted scopes and the token set encrypted as one value. One Google account serves both a Gmail and a Calendar connection.
- `credential_version` is bumped by every change to the tokens, which happen only inside a transaction holding the row with `FOR UPDATE`, so two workers never refresh at once or lose a rotated refresh token.
- `status` is `connected`, `needs_reconnect` (the provider ended the grant) or `revoked`, and `notified_at` makes the "needs reconnecting" notification happen once.
- A **connection** of kind `gmail`, `google_calendar` or `notion` points at its account (`on delete restrict`), with the `capabilities` you allowed, `ask_before_acting`, Notion's teammates' area in `settings`, and a `revision` bumped by every change to who may use it and how. A check constraint keeps MCP and account connections apart.
- **`oauth_states`** holds a sign-in in progress for 10 minutes: the state, the encrypted PKCE verifier, the session that started it, and what it asks for, including the identity a reconnect must come back as.

### Account actions

`account_actions` is the queue and the record of every change teammates make.
A row is inserted with its approval, already linked, holding the exact provider request, the effect class, the connection's revision when it was asked for, and the labels its timeline item shows.

```text title="An action's states"
pending ──► approved ──► executing ──► done
   │           │           │   ▲       failed
   │           │           │   │       unknown    the answer was lost, and the account can't tell
   │           │           ▼   │
   │           │     waiting_on_provider          Notion's background task, up to 15 minutes
   │           │
   │           └──► cancelled                     turned off, changed, or access taken away
   ├──► cancelled
   ├──► denied
   └──► expired                                   not decided within 7 days
```

Only pending and approved actions can still change course.
Executing holds a 5-minute lease, and a stopped action whose lease ran out is reconciled with the provider, never simply run again.

- Deciding the approval moves `pending` to `approved` or `denied` in the same transaction, then sends `NOTIFY openbot_worker, 'accounts'`.
- The executor claims an action with an `UPDATE … WHERE status = 'approved'` and bumps `attempt`; `next_check_at` holds the lease, or when to poll Notion again.
- `provider_ref` keeps what the provider returned, like the event id and etag or the sent message id, and `result` what the teammate is told.
- `reported_at` is set when the outcome reached the timeline and, for `denied`, `failed`, `unknown`, `cancelled` and `expired`, a follow-up run. Finished rows without it are still to be reported, so an outcome is told once, even across a restart.

`account_resources` records Notion pages and databases teammates created, so later changes to them follow the teammate's autonomy instead of always asking.

## Usage ledger

`usage_entries` records tokens per run and auth mode, with an idempotency key of `run:<id>:<mode>` so a retry can't count twice.
Plan usage costs nothing per token, so its `cost_micros` is 0.
API key usage is priced at the model's list prices, in millionths of a dollar.
See [Models and usage](/docs/flows/models-and-usage#the-monthly-cap).
