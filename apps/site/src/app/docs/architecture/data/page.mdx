# Data and events

Postgres is the system of record, the job queue, the event log and the message bus.
This page covers the schema, how runs are queued, how events are stored and streamed, and the three `NOTIFY` channels.

### Conventions

- Primary keys are random UUIDs, except `run_events.id`, which is a `bigserial` so events have a global order.
- Timestamps are `timestamptz`.
- Structured values (attachments, timeline payloads, approval payloads) are `jsonb` with a TypeScript type attached with `$type<>()`.
- Deleting a teammate archives it (`teammates.archived_at`). Rows that belong to it cascade or set null as each foreign key says.
- Secrets are never stored in plain text. `encryptSecret()` in `@open-bot/domain/server` uses AES-256-GCM with a random 12-byte IV, and stores `iv.tag.ciphertext` in base64url.
- The settings row is read only through `ownerSettings()` and `ownerTimeZone()` in `packages/db/src/settings.ts`, so a missing row means the same defaults everywhere.

### One writer per table

Every table has one owner, the one module that inserts, updates and deletes its rows, listed in `packages/db/src/owners.ts`.
Most owners are worker services; the web app changes their tables through the worker's internal API.
Any server code may read any table.
The `open-bot/table-owners` lint rule fails a write anywhere but the owner, so a rule about a table (a lock, a revision check, an event to publish) lives in one place.
A module that must change a few columns in its own transaction, like memory stopping the turns that read old memory, is listed under `shared` with those columns, and the rule lets it set only them.
`pnpm test:scripts` fails when a `shared` entry no longer writes its table, so the list only shrinks.

Advisory locks are named in `LOCKS` in `packages/db/src/locks.ts` and taken with `lockUntilCommit()`.
Their keys never change once shipped, because the web app and the worker deploy separately and must still exclude each other.

### Migrations

Migrations are generated SQL files in `packages/db/drizzle/`; `meta/_journal.json` records their authoritative order.

```sh title="Terminal"
pnpm db:generate   # write a new migration from changes to the schema
pnpm db:migrate    # apply pending migrations
```

`0020` runs `CREATE EXTENSION IF NOT EXISTS vector`, so the database must have pgvector available.
The local Compose file uses the `pgvector/pgvector:pg17` image.

### Failed queries

A query's parameters can hold anything the owner typed, and anything may log a failed query's error whole, including Next.js and Better Auth for errors no code caught.
So values are taken out where the error is made (`packages/db/src/errors.ts`).
Drizzle's `DrizzleQueryError` is patched (`patches/drizzle-orm@0.45.4.patch`) so it never keeps the parameters, and its message is only the failed SQL.
Every pool from `createPool` uses a client that rebuilds Postgres's own error without `detail`, `where`, `hint` or `internalQuery`.
Its message stays when its SQLSTATE class only names things (a constraint violation, a deadlock, a missing column), and otherwise becomes `The database refused the query (SQLSTATE 22021).`, since a data error's message can quote the value it refused.

### Lost connections

When the database restarts or ends a connection, every idle connection a pool holds fails at once.
`createPool(url, { onIdleError })` takes a handler for that, so each app logs it (without values) instead of crashing on the pool's unhandled `error` event; the pool has already dropped the connection and opens a new one when it next needs it.
A connection taken out of the pool, by a transaction say, fails its next query instead, so whoever holds it hears about it; `createPool` gives every connection an `error` listener, since the pool listens only while it holds one.
One kept to `LISTEN` adds its own listener to replace it.
A transaction gives its connection back to the pool however it ends, even when the connection is lost while `begin` is still running.
Upstream Drizzle runs `begin` before its `try`, so such a connection stayed taken out forever: the pool kept counting it, and `pool.end()` never resolved, which hangs the worker's shutdown.
The same patch (`patches/drizzle-orm@0.45.4.patch`) moves `begin` inside, and gives a connection whose `begin` or `rollback` failed back with that error, so the pool closes it; `packages/db/src/pool.integration.test.ts` cuts a connection at `begin` to check it.
The worker's `SignalListener` (`apps/worker/src/signal-listener.ts`) drops a failed one, listens again on a new one (waiting from 1 s up to 30 s between tries), and then answers every signal once, since any sent in between were missed.

## The run queue

A queued run is a row in `runs` with `status = 'queued'`.
Anything that wants a teammate to work calls `enqueueRun()` (`apps/worker/src/runs/queue.ts`), which:

1. inserts the run with its trigger, prompt and links (the message, schedule, trigger or parent run that caused it);
2. appends a first `status: queued` event, so the chat shows it right away;
3. sends `NOTIFY openbot_worker, 'runs'`.

The worker claims runs with `UPDATE ... FOR UPDATE SKIP LOCKED`, at most one per teammate per lane of a chat, oldest first.
The query is on the [Worker](/docs/architecture/worker#claiming-work) page.

`runs.waiting_for` says what a waiting run waits for: `approval` or `takeover`.

`runs.lane` is the lane of the chat it works in (see [Threads](/docs/architecture/agent-runtime#threads)).
`runs.quiet` marks a quiet routine's run that had nothing to report; it doesn't count as activity in the chat.
`runs.passed_on_at` is when a run outside the `chat` lane was passed on to its chat's conversation.

## The event log

`run_events` is append-only.
Each row has the run id, the chat id (so a chat's events are one index scan), and a jsonb `payload` of one of four types:

```ts title="RunEventPayload (packages/domain/src/timeline/timeline.ts)"
type RunEventPayload =
  | { type: "status"; status: RunStatus; error?: string; waitingFor?: "approval" | "takeover" }
  | { type: "item"; item: TimelineItem } // insert or replace an item by id
  | { type: "delta"; itemId: string; delta: string } // append text to an item
  | { type: "usage"; inputTokens: number; cachedInputTokens: number; outputTokens: number };
```

A `TimelineItem` is one thing the run did, with an `id`, a `status` (`running`, `completed` or `failed`) and timestamps.
There are fourteen kinds: `message`, `reasoning`, `command`, `file_change`, `plan`, `web_search`, `tool`, `computer` (a desktop action with its screenshot), `approval`, `takeover_request`, `handoff`, `user_message` (steering and hand-back notes), `swarm` and `error`.

Items are written whole whenever they change, and the reducer replaces them by id.
Deltas only append text.
This keeps the reducer simple and makes the log easy to read in SQL.

`applyRunEvent(state, payload)` in `@open-bot/domain` folds events into a run's timeline.
It is pure and shared: the web app uses it on the server to build a chat's first snapshot, and in the browser to apply live events.

### Why a log

- **Streaming.** The stream route reads rows after a cursor, so streaming is just a query.
- **Resuming.** A tab that reconnects sends its last id and gets exactly what it missed.
- **Replay.** Every desktop action points to its screenshot in `artifacts`, so you can step through what a teammate did, frame by frame, at any later time.
- **Late updates.** An approval decided after its run ended still appends an event to that run (`appendRunEvent`), so the card in the chat updates.

## Notification channels

`packages/domain/src/events/notify.ts` defines three channels (`NOTIFY_CHANNELS`), and `notify()` in `packages/db/src/index.ts` sends on them:

| Channel          | Payload                                                 | Sent by                              | Listened to by            |
| ---------------- | ------------------------------------------------------- | ------------------------------------ | ------------------------- |
| `openbot_worker` | `runs`, `schedules`, `triggers`, `accounts` or `cancel` | the web app and the worker           | the worker                |
| `openbot_chat`   | a chat id                                               | the worker, after storing run events | the web app's SSE streams |
| `openbot_app`    | a JSON `AppEvent`, like `{"type":"approvals"}`          | the web app and the worker           | the web app's SSE streams |

`AppEvent` has about twenty types, one per area of the UI: `teammates`, `chats`, `approvals`, `takeovers`, `lease`, `computer`, `notification`, `schedules`, `triggers`, `tasks`, `memory`, `vault`, `purchases`, `connections`, `email`, `telegram`, `skills`, `pages`, `profile`, `lessons`, `auth`, `settings` and `modelLogs`.
Each one tells open tabs which cached queries to refetch.

Notifications are hints, not data.
Every listener reads the rows itself, and the worker sweeps for queued runs and cancellations every 15 seconds, so a dropped notification only delays something.

## Accounts

Your Gmail, Google Calendar and Notion are three tables and two kinds of `connections` row.
See [Your accounts](/docs/flows/accounts) for what you see.

- An **`account_connections`** row is one sign-in: Google's `sub`, or Notion's workspace and user, unique per provider, with the granted scopes and the token set encrypted as one value. One Google account serves both a Gmail and a Calendar connection.
- `credential_version` is bumped by every change to the tokens, which happen only inside a transaction holding the row with `FOR UPDATE`, so two workers never refresh at once or lose a rotated refresh token.
- `status` is `connected`, `needs_reconnect` (the provider ended the grant) or `revoked`, and `notified_at` makes the "needs reconnecting" notification happen once.
- A **connection** of kind `gmail`, `google_calendar` or `notion` points at its account (`on delete restrict`), with the `capabilities` you allowed, `ask_before_acting`, Notion's teammates' area in `settings`, and a `revision` bumped by every change to who may use it and how. A check constraint keeps MCP and account connections apart.
- **`oauth_states`** holds a sign-in in progress for 10 minutes: the state, the encrypted PKCE verifier, the session that started it, and what it asks for, including the identity a reconnect must come back as.

### Account actions

`account_actions` is the queue and the record of every change teammates make.
A row is inserted with its approval, already linked, holding the exact provider request, the effect class, the connection's revision when it was asked for, and the labels its timeline item shows.

```text title="An action's states"
pending ──► approved ──► executing ──► done
   │           │           │   ▲       failed
   │           │           │   │       unknown    the answer was lost, and the account can't tell
   │           │           ▼   │
   │           │     waiting_on_provider          Notion's background task, up to 15 minutes
   │           │
   │           └──► cancelled                     turned off, changed, or access taken away
   ├──► cancelled
   ├──► denied
   └──► expired                                   not decided within 7 days
```

Only pending and approved actions can still change course.
Executing holds a 5-minute lease, and a stopped action whose lease ran out is reconciled with the provider, never simply run again.

- Deciding the approval moves `pending` to `approved` or `denied` in the same transaction, then sends `NOTIFY openbot_worker, 'accounts'`.
- The executor claims an action with an `UPDATE … WHERE status = 'approved'` and bumps `attempt`; `next_check_at` holds the lease, or when to poll Notion again.
- `provider_ref` keeps what the provider returned, like the event id and etag or the sent message id, and `result` what the teammate is told.
- `reported_at` is set when the outcome reached the timeline and, for `denied`, `failed`, `unknown`, `cancelled` and `expired`, a follow-up run. Finished rows without it are still to be reported, so an outcome is told once, even across a restart.

`account_resources` records Notion pages and databases teammates created, so later changes to them follow the teammate's autonomy instead of always asking.

## Usage

Usage has two producers, and each request counts through one of them.
A worker that writes the old ledger, `usage_entries`, counts its runs there, and they become the legacy totals below.
The current worker writes no ledger: each request it logs in `model_requests` carries its tokens and its `cost_micros`, and `counts_usage` set; the requests an older worker logged leave it false.
No clock decides which side a request is on, so clock skew, a rollback and a redeploy count each request once, and every reader (the reply footer, Settings and the monthly cap) counts usage the same way.
Plan usage costs nothing per token, so its `cost_micros` is 0.
API key usage is priced at the model's list prices, in millionths of a dollar.

The legacy totals are what the old ledger, `usage_entries`, held for each run.
Migration 0040 copied them onto the run, per access mode, through `copy_legacy_usage()`, and a trigger on `usage_entries` copied each entry written after it, so the totals hold every entry; only migrations and their triggers write these columns of `runs`:

- `legacy_plan_input_tokens`, `legacy_plan_cached_input_tokens`, `legacy_plan_output_tokens` and `legacy_plan_cost_micros`, for the ChatGPT plan.
- `legacy_api_key_input_tokens`, `legacy_api_key_cached_input_tokens`, `legacy_api_key_output_tokens` and `legacy_api_key_cost_micros`, for the API key.
- `legacy_usage_at`, when the run's usage was counted: when its API key entry was written, else its plan entry.
  `runs_legacy_usage_idx` finds a month's runs by it.

A mode the run never used stays null.
Ledger entries whose run was already deleted go to `legacy_deleted_run_usage`, one row per entry, keyed by the entry's own key (`run:<id>:<mode>`), with its teammate and time, so they still count toward their month.
The `runs_keep_legacy_usage` trigger moves a run's legacy totals there too, under the same keys, whenever a run with them is deleted.
Both copies skip a key they already hold, so migration 0041 ran the copy once more, under a lock, before it dropped `usage_entries`.

`apiKeySpendMicros()` in `packages/db/src/usage.ts` adds up the API key's spend for the cap and Settings: counted API key requests, the cost `model_log_gaps.api_cost_micros` keeps of lost ones, and the legacy totals.
`model_requests_api_started_idx`, partial on counted API key requests, keeps its sum of the month's requests small.
See [Models and usage](/docs/flows/models-and-usage#the-monthly-cap).

## Model logs

Every model request that goes through the [model proxy](/docs/architecture/agent-runtime#the-model-proxy) is saved by one buffered writer (`apps/worker/src/features/model-logs/writer.ts`), which owns the seven tables.
So are the requests of the [memory AI](/docs/flows/memory#optional-ai), with `source` `memory`.

- `model_requests` has one row per request: the route (`plan` or `api`), the transport (`http` or `websocket`), the method (over a WebSocket, the message type `response.create`), the endpoint, the HTTP status (over a WebSocket, 200 once the response streams, or an error's own status), when it started, sent its first byte and ended, the token counts and `cost_micros` from the response's usage (or, for an API key request that ended without reporting it, an estimate that errs high, with `usage_estimated` set), how it ended (`stop_reason`, `error_type`, `error_message`), its headers without credentials, the rate-limit headers, and the response's text and reasoning summary.
  `params` holds the request body without its input, instructions and tools; it is left out, with a warning, when it nests more than 256 levels deep.
  `raw_response` holds the first 1 MiB of a response only when it could not be rebuilt: a stream cut short, or JSON that isn't a Responses API response (search results, images).
  `parse_warnings` says why, and when the response was cut to fit.
  When the proxy can't read a response, or can't put a request's record together (an item nested too deeply to serialize), the request is still logged, without what failed and with a warning that says why.
- `codex_thread_id`, `codex_turn_id` and `request_kind` come from the request's own turn metadata.
  Requests are linked to runs through them when they are read, never with a run id resolved when they are written, because a request can arrive before the worker has saved the turn's id.
  `teammate_id` is the teammate whose live run the proxy let the request through for.
- `model_blobs` stores each distinct input or output item, the instructions and the tool list once, as JSON under its SHA-256.
  Every request sends the conversation so far again, so a request adds only its new items.
  The writer looks up which hashes exist and sends only the new blobs.
  `content` is compressed with lz4 where the server supports it (the `pgvector/pgvector:pg17` image does).
- `model_request_items` lists a request's items in order, on the `input` and `output` sides.
  A request is rebuilt exactly as Codex sent it from `params`, the instructions and tools blobs, and its input items.
- Over a WebSocket, Codex sends only the items a request adds to the one before it, with a `previous_response_id`; the stored input is the full one the model saw, rebuilt by the proxy.
  `sent_input_from` is where the items the message itself sent begin, so the message rebuilds as sent from `params` and the input from that position on.
  It is empty when the stored input is what was sent.
- `model_log_gaps` records requests that were lost: dropped after 5 minutes without reaching the database, past the 64 MB queue, or refused by the database itself.
  Its row is written once the database answers again, with how many requests, Codex events (`codex_events`) and turns (`run_turns`) were lost.
  Each gap holds the records of one calendar month (UTC), counts the lost API key requests and what they cost (`api_requests`, `api_cost_micros`), which the cap adds to the month they started in, and how many of those costs are estimates (`api_requests_estimated`).
  A request naming a teammate deleted since it was made is kept, with `teammate_id` empty.

Bodies and item contents are stored as sent, encrypted reasoning included, so a request can be sent again exactly.
Headers that carry credentials (authorization, cookies, API keys, tokens, secrets) are never stored, and neither is `chatgpt-account-id`, which names the ChatGPT account.
The same goes for header objects inside what the model sent back, in `raw_response` and `error_message`.
A header object is the value of a `headers` key, in any case, at any depth, like the `headers` of a WebSocket event or an error envelope.
An object there loses the same headers, and anything else under that key (a list, a string) is left out whole.
`raw_response` is read message by message over a WebSocket, event by event in an event stream (an event's `data:` lines as one), and whole for any other body.
A message, an event's data or a body that can't be read whole as JSON (cut by the 1 MiB limit, not JSON, or nested more than 256 levels deep) loses everything from its first `headers` key to its own end, the lines after that key included, and `parse_warnings` says the raw response was cut.
A line of an event stream outside an event's data, such as a comment, is cut at its first `headers` key too.
An error with no message of its own stores its envelope in `error_message`, redacted the same way, or a note that it was nested too deeply to keep.
Credentials anywhere else in a body, such as inside a string or under another key, are stored as sent.
A WebSocket's rows leave out the handshake's own headers (`sec-websocket-*`, `connection`, `upgrade`) and its turn metadata, since each message names its own turn.

A memory AI request (`source` `memory`) has no route, thread or turn: its `endpoint` is the configured URL without credentials, query or fragment, `request_kind` is `extraction` or `embedding`, its messages or embedded text are its input items, and its answer or vector is its output.
Its stored headers are only `content-type`; the memory AI key is never stored.

### Codex events, turns and tool calls

The same writer saves what the worker sees of Codex itself (see [Agent runtime](/docs/architecture/agent-runtime#the-codex-event-log)).

- `codex_events` has one row per JSON-RPC message between the worker and Codex, except streaming deltas.
  It holds the `direction` (`to_codex` or `from_codex`), the `kind` (`request`, `response` or `notification`), the `method` (a response's is its request's), the `rpc_id`, the `sequence`, the time (`at`), and the thread, turn and item the message names.
  `payload` is the redacted params of a request or notification, or the `result` or `error` of a response, compressed with lz4 where the server supports it.
  A message too large, too deep or too complex to store keeps a stub: `{ "omitted": why, "size": characters }`, and is counted in `model_log_gaps`.
  `run_id` is the run the message belongs to, and is empty for messages outside any run.
  `delta_counts` on an `item/completed` row counts the deltas that streamed the item, by method; on `turn/completed` it holds the counts of items that never completed.
- `run_turns` has one row per Codex turn a run started, written when `turn/start` returns: the run, the thread and turn, `access_mode` (`plan` or `api_key`) and `started_at`.
  It is how a run's model requests are found: `model_requests` joins it on `codex_thread_id` and `codex_turn_id`.
  A run that falls back from the plan to the API key mid-run has two turns, on two threads.
- `model_tool_calls` lists the tool calls in each response's output, by `position`.
  Each has its `call_id`, the output item's `type` (`function_call`, `custom_tool_call`, `local_shell_call`, `web_search_call`, `mcp_call`, ...), its `name`, its `namespace` (an MCP tool's server) and its `arguments` as the model sent them.
  A web search has no call id, so its `call_id` is the output item's own id.

Messages and turns of a run deleted before they are saved are dropped, and those saved before go with the run.

#### Joining a tool call to its outcome

Codex names the app-server item for a direct tool call by the call's `call_id`.
So a call joins its outcome in `codex_events` on the request's `codex_thread_id` and the call's `call_id`, matched to the event's `codex_thread_id` and `item_id` (the `codex_events_item_idx` index):

- a shell command is a `commandExecution` item, whose `item/completed` row has its `exitCode`, `status` and `durationMs`;
- a file edit is a `fileChange` item, with its `status`;
- an MCP tool is an `mcpToolCall` item, with its `error` when it failed;
- an open-bot tool is a dynamic tool call: Codex's `item/tool/call` request names it by `callId`, and the worker's result is the `to_codex` response with that request's `rpc_id`, which carries the same `item_id`;
- a web search is a `webSearch` item, named by the output item's id.

Code mode wraps calls.
There the model makes one `custom_tool_call` named `exec`, whose `arguments` are JavaScript that calls the tools.
Codex gives each nested call an item id of its own (`exec-<uuid>`) that nothing else names: no model request, and no app-server message, ties it to its cell (checked against Codex 0.162.1).
So a nested item is linked to the cells that could have been running when it started, and never claimed as exact.
`linkToolItems` in `@open-bot/domain` (`packages/domain/src/model-logs/tool-links.ts`) does this from a thread's model requests, their tool calls, the tool outputs in their input, and the thread's tool items:

- A cell can start once its response starts streaming: Codex starts it as soon as the call's output item is done, before the response ends, so its window opens at the request's `first_byte_at`.
- The model sees a cell's result as its `exec` output, whose first line is its status (`format_script_status` in Codex's `core/src/tools/code_mode/mod.rs`).
  `Script completed`, `Script failed` or `Script terminated`, as the whole first line, mean it ended, so its window closes when the first request carrying that output started, plus 2 seconds for an item's message to arrive over the app-server connection after the request arrived over the model proxy.
  An output with no status line is an error that says nothing about the cell (a `wait` whose arguments didn't parse, or a failure after the cell started), so it leaves the window open.
- `Script running with cell ID <id>` means it yielded and runs on across later requests.
  Its window stays open until a `wait` call on that cell id returns one of the ending statuses, and stays open to the end of the logs when none does.
- An item is matched by when it started (`item/started`, else its `item/completed`).
  It is `exact` when its id is a call's `call_id`, `only_candidate` when one cell's window holds it, `ambiguous` when several do (all listed), and `none` when no call explains it.
  `only_candidate` is an inference from timing, not a fact the logs record.
  Several `exec` calls in one response, or a yielded cell running beside a new one, make their items `ambiguous`.

Each nested item has its outcome in its own `item/completed` row, as above.

### Where they are shown

The owner reads the logs in the web app, under Settings, Model logs (`/settings/model-logs`).
It lists the runs that have logs, newest first, with their teammate, chat, start time, model requests, tokens, cost and errors.
Each run opens its inspector (`/settings/model-logs/runs/<run id>`), which a teammate's reply also links to from its menu, as Inspect model requests.
The inspector shows the run's turns and each request in them, with its kind, model, access mode, status, timing, tokens, cost, rate limits and parse warnings.
A request that failed shows its error, and the next request of the same kind in the same turn is marked as its retry.
A prewarm has no turn id, so it is placed by time, and says so.
Out of every turn of its thread, from any run, it goes to the latest one that had started when it was sent, if that turn's run was still going; else to the next one, if that started within 10 seconds after it, since Codex can send a prewarm before `turn/start` returns and the turn is saved.
So each prewarm counts toward one run only, in the list's totals and in the inspector alike (`unturnedTurnSql` in `apps/web/src/features/model-logs/server/attribution.ts`).
The list's search and filters, the Usage tab and the export attribute requests by the same rule (`requestOfTurn` in the same file).
The lookup walks the thread's turns in start order through the `run_turns_thread_started_idx` index, and runs only for requests between the turn's start, less the slack, and its run's end.
A run with more than 500 requests lists its first 500, says so, and counts all of them in its totals.
What the last listed calls did after the cut still shows: an item that started before the cut keeps its completion, a listed call's own item shows whenever it was reported, and a code-mode cell keeps the items that started while it was known to run.
What they got back comes from the first request left out in each thread, whose input carries it.
Items that started after the cut and that no listed call explains belong to requests that aren't listed, and are left out.
What each tool call got back is worked out from the requests' input history, which repeats every earlier item in each request.
The history is first cut down to where each item of a thread first appeared; only then is each distinct output item parsed and its preview cut, once, so that work grows with the number of calls, not with how often later requests repeated them.
The list pages by creation time and run id together, at full precision, so runs created in the same instant are never skipped.
A page cursor whose time doesn't exist, like a 13th month or a 30th of February, is refused as a bad request.
The worker announces a `modelLogs` app event once a batch of logs is saved, at most every 2 seconds (`apps/worker/src/features/model-logs/announcer.ts`), which refreshes the list; it leaves the shell's state and Home alone.
At shutdown the writer drains first, while the announcer still listens, and the announcer sends what that saved before it stops.
Expanding a request loads its bodies: the input items labeled by role and type, with those carried over from the WebSocket's earlier messages set apart, then the instructions, the tools, the response with its reasoning summary, and the request's parameters and headers.
Each tool call shows its outcome joined as above.
A code-mode cell lists the nested items linked to it, each marked as likely when it was the only candidate, or uncertain when several cells could have run it.
The run's Codex messages are listed last, collapsed, and each payload loads when it is opened; a stub says it was not stored, and why.
Bodies are shown as text, never as HTML.
The procedures are `modelLogs.runs`, `modelLogs.run`, `modelLogs.request`, `modelLogs.events` and `modelLogs.event` (`packages/api/src/contracts/model-logs.ts`), which read the tables directly from the web app (`apps/web/src/features/model-logs/server/`) and need the owner's session.
How a run's requests, tool calls and outcomes are put together is pure logic in `@open-bot/domain` (`packages/domain/src/model-logs/run-view.ts` and `items.ts`).

### Browsing and search

The Runs tab filters the list by teammate, chat, model, status (done, failed, stopped, working, or any run with a failed request), access mode (plan or API key) and dates.
The filters live in the page's address, so a filtered view reloads and goes back as it was.
Dates are whole days in the browser's time zone.
The search box finds runs by what was sent and what came back: the stored items, the instructions and the tool definitions in `model_blobs`, and each response's text.
A blob that matches is followed to every request that names it, as an item, as its instructions or as its tools.
It is Postgres full-text search with the `simple` configuration, read with `websearch_to_tsquery`, so quotes find a phrase, `-` leaves a word out, and nothing typed can break the query.
Two GIN expression indexes serve it, `model_blobs_search_idx` and `model_requests_response_search_idx`, over the first 100,000 characters of each text (`MODEL_LOG_SEARCH_CHARS`), which keeps every document under Postgres's 1 MB `tsvector` limit.
A blob is stored as JSON, so it is searched by its string values decoded, never by its JSON text: a word after a newline is its own word, and `\"` or `\u00e9` read as the characters they stand for.
The function `model_blob_search_text` (created by migration `0039`) gives that text, without object keys, the values of structural fields (`type`, `role`, `status`, `id`, `call_id`) or encrypted reasoning; the index, the search and the snippet all call it the same way.
A blob that jsonb can't read (a NUL kept as `\u0000`, or text that isn't JSON), or one over a million characters, is read as its text with the escapes undone instead, so indexing never fails a write.
Queries that parse blobs for other reasons use `model_blob_jsonb`, which gives null for such a blob rather than failing the query.
A match shows a snippet from `ts_headline` with the words that matched marked, on one line, with at most four words before the first match so it stays in view.
The snippet is cut from 4,000 characters around the first place a searched word appears, so it costs the same wherever in the first 100,000 characters the match is.
That window is used only when the whole search matches it; otherwise (the word was found inside another one, or a phrase or another word is further on) the whole searchable text is read.
Requests whose bodies have expired are not searched.
Pages are read by keyset, never by offset: each page's cursor is the last run's creation time to the microsecond and its id (`runs_created_idx`), validated as above.

### Tools

The Tools tab (`/settings/model-logs/tools`) counts each tool's calls over a range, across teammates: how many failed, how many outcomes were too large to keep, and the median and slowest 5% of durations.
It reads the `item/completed` rows of `codex_events` (`codex_events_completed_idx`), so it counts every call Codex made, nested ones included.
Below the table, its failures are listed newest first, each with its input and output, and a link to its run.
Each failure says how sure the link to the model's call is, in the words of the inspector: called exactly, likely made by the only code cell running then, or one of several cells.
An expired failure keeps its tool, status and a short error, without its input or output.

### Usage

The Usage tab (`/settings/model-logs/usage`) reads only `model_requests`, so it starts when model logging did; runs finished before then count only in Settings' own usage view, from their [legacy totals](#usage).
It shows tokens (input, cached input, output and reasoning), the cached share, the cost on the API key and failed requests, by day in the owner's time zone, or by week (Monday first) over ranges longer than 92 days.
The same numbers are listed per teammate and per model, and per day as a table.
A request belongs to its run's teammate, or to the teammate the proxy let it through for when its run is gone.
The plan's usage windows are drawn from the rate-limit headers stored on each plan response: the highest reading each hour over ranges up to 3 days, and each day's peak over longer ones.
This calendar month's API key spend, from the model logs, is shown against the monthly cap.
The month is a UTC calendar month, as the cap counts it, and is labeled that way ("November (UTC)").
A range can span at most 400 days.

### Retention

The owner chooses how long model logs keep their bodies, in the Retention tab (`/settings/model-logs/retention`): forever, which is the default, or from 7 days to a year.
The choice is `settings.model_log_retention_days`, empty for forever, and is saved through the worker (`POST /internal/settings/model-log-retention`).
A sweep in the worker (`apps/worker/src/features/model-logs/retention.ts`) runs 2 minutes after start, then once a day, and again right after the choice changes.
It removes the bodies of everything logged before the window, oldest first:

- for a request, its items, instructions and tools, its response text, reasoning summary and raw response, its tool calls' arguments, and every parameter but those that say how it was asked, then sets `bodies_expired_at`;
- for a Codex message, its payload down to what the item was, how it ended and the tool it named (`EXPIRED_ITEM_FIELDS`), with an error cut to 300 characters, then sets `bodies_expired_at`;
- then the blobs nothing names any more.

Numbers, statuses, error messages, tool names and links stay, so the Runs, Tools and Usage tabs keep their numbers.
A request's parameters can carry text too: a Responses `input` that isn't a list stays in `params`, and other endpoints send prompts and metadata there.
So an expired request keeps only the parameters a list names (`expiredParams` in `packages/domain/src/model-logs/retention.ts`): the model, effort, limits, flags and the like, with plain values.
A field the list doesn't name is removed, so a new one is never kept by accident.
Each batch is its own short transaction, locked with `FOR UPDATE SKIP LOCKED`, and the partial indexes `model_requests_unexpired_idx` and `codex_events_unexpired_idx` find what is left.
A blob is deleted only once no request names it; the writer takes a `FOR KEY SHARE` lock on the blobs it reuses, and a delete that meets a blob the writer named meanwhile is tried again without it.
One sweep runs at a time, across workers too (an advisory lock), and shutdown stops it between batches, before the writer drains; the next sweep goes on from there.
The inspector says when a run's bodies expired, and marks each expired request.

### Export

The inspector and the runs list link to a JSONL export (`GET /api/model-logs/export`): every request of one run (`?runId=`), or of a range of dates (`?from=&to=`), oldest first, one JSON object per line.
Each line holds the request rebuilt in full, as it was sent, with its response and everything else known about it (`exportLine` in `packages/domain/src/model-logs/export.ts`).
The body takes the shape of the API it called (`rebuildRequestBody`), told apart by the stored endpoint and, for memory, what the call did:

- a Responses request gets its items back under `input`, unless its `input` wasn't a list, which then stays as it was in the parameters;
- a chat completion (memory extraction) gets them back under `messages`;
- an embedding gets its one string back under `input`, or its list.

Storage can't tell an embedding of a one-string list from one of that string, and both ask the embeddings API the same thing; memory only sends a string.
An empty input list is left out of the rebuilt body.
The inspector's "Copy body" uses the same function.
A range takes every request in its dates, whatever the list's other filters, including requests that belong to no run.
The export streams: it reads 25 requests at a time, each request's bodies on their own, and only as fast as the download takes them, so no run or range is held in memory whole and nothing is capped.
An expired request is exported without its bodies (`request` and `response` are null), with only the parameters retention keeps, and says when they expired, as the inspector does.
