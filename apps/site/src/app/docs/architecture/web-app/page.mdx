# Web app

`apps/web` is a Next.js 16 app with the App Router, React 19 and Tailwind 4.
It serves the browser UI and the Android app's API: it reads Postgres directly, and asks the worker to do anything that acts.

## What talks to what

- **Pages** (`src/app/(app)/*`) are server components. They check the session and render the first view from Postgres, so a page is useful before any client code runs.
- **The API and uploads** (`/api/rpc/*`, `PUT /api/uploads/:id`, `PUT /api/files/upload`) serve the browser and the Android app through feature-local services and routes.
  `src/lib/server/api/router.ts` only composes those routes; `rpc.ts` supplies session middleware and error mapping.
  Every browser write goes there, with `attempt()` (`src/lib/client/mutate.ts`): there are no server actions, and `src/no-server-actions.test.ts` fails if one is added.
  See [Internal APIs](/docs/reference/http-api#the-api) for their entry points and authoritative contract.
- **Reads** go through the API (`@open-bot/api`), the same procedures the Android app calls.
  Client components query them with TanStack Query through `orpc` (`src/lib/client/rpc.ts`), whose cache keys are procedure paths.
  Next.js runs server actions one at a time per client, so reads and writes done as actions queued behind each other and made pages slow; that is one reason the app has none.
  Server components read through a feature's `server.ts`, never the database directly.
- **Features** (`src/features/<feature>/`) keep their views in `components/`, browser hooks in `hooks.ts`, and reads, services and API procedures in `server/`.
  Other code reaches a feature only through its `index.ts`, or `server.ts` for its server side, which `src/features/boundaries.test.ts` checks.
  The test also refuses server code (the database, `server-only`) anywhere `index.ts` reaches, since that entry ends up in the browser.
  Ownership follows the UI: `app-shell` assembles app state and attention and supplies the shared shell hooks; `notifications` owns the popover, its list and mark-read.
  `settings` owns the profile and browsing/egress, including paired-device authentication; `teammates` and `chat` own their lists.
  Chat attachment uploads live in `chat`, while folder uploads live in `files`.
  Shared auth, session, DB, env, realtime, publishing, RPC and worker-client/status infrastructure stays in `src/lib/`.
  Feature-local integration suites exercise the real router with a disposable database and a worker stand-in per suite, using `src/test/api/harness.ts` and `src/test/api/seed.ts`; the shell suite retains cross-feature composition checks.
- **The event stream** (`GET /api/stream`) is one server-sent events connection per tab. It tells the tab when anything changes, and streams the run events of the chat on screen.

The browser never talks to Codex or botd.
The only connection outside the web server is the live screen, which goes from the browser straight to the worker's `/vnc` websocket.

## Authentication

open-bot belongs to one person, and the web app enforces it.

- **Better Auth** stores users, sessions, accounts and passkeys in Postgres through its Drizzle adapter.
- **Email and password** (at least 10 characters) and **passkeys** are both supported. A passkey's relying party is the host of `BETTER_AUTH_URL`.
- **One owner.** A database hook runs before any user is created. It refuses an email that isn't `OWNER_EMAIL`, and refuses any second account.
- **Sessions** last 30 days and are refreshed daily. The Electron app's `app://open-bot` origin is trusted alongside the web origin.

Every protected surface checks the session itself:

| Surface                                            | Check                                                                                                  |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Middleware (`src/proxy.ts`)                        | Redirects to `/login` when there is no session cookie. It's an optimistic check only.                  |
| Pages                                              | `requireUser()` verifies the session and redirects to `/login`, or to `/setup` if no owner exists yet. |
| Read and upload routes                             | `authed()` returns `401` without a session, and maps worker errors to their status.                    |
| RPC handler                                        | Its middleware verifies the session before invoking a procedure.                                       |
| `/api/hooks/[token]`, `/api/inbound/email/[token]` | Public on purpose. The secret token in the URL is the credential.                                      |

## Calling the worker

`src/lib/server/worker.ts` is a small `fetch` wrapper.
It sends the shared `WORKER_SECRET` in an `x-worker-secret` header, times out after 30 seconds by default, and throws a `WorkerError` with the worker's status and message.
If the worker can't be reached at all, the error is a 503 that says to start it.

Message persistence and dispatch retries are described in [Saving the message](/docs/flows/chat-turn#saving-the-message); the worker's chat service (`apps/worker/src/features/chat/service.ts`) saves every message.

## Live updates

### On the server

`src/lib/server/realtime.ts` holds **one** Postgres connection per server process, listening on two channels:

- `openbot_chat`, whose payload is a chat id: something in that chat changed.
- `openbot_app`, whose payload is a small JSON event like `{"type":"approvals"}`: something app-wide changed.

It fans each notification out to every open SSE stream in that process with an `EventEmitter`.
A stream never holds its own database connection.

### The stream route

`GET /api/stream?chat=<id>&after=<cursor>` sends three kinds of events:

| Event   | Data                                                     | Sent when                                  |
| ------- | -------------------------------------------------------- | ------------------------------------------ |
| `ready` | `{ cursor, deployment }`                                 | The stream opens.                          |
| `app`   | an `AppEvent`, like `{"type":"notification","id":"..."}` | Any `openbot_app` notification.            |
| `run`   | `{ id, runId, payload }`, a row of `run_events`          | A new event in the watched chat, in order. |

For the watched chat, the route keeps a cursor.
On every `openbot_chat` notification for that chat, it selects rows with `id > cursor` in pages of 500, sends them, and advances the cursor.
The work is serialized through a promise chain, so a burst of notifications can never send an event twice or out of order.
It also catches up once right after opening, which covers anything written between the page load and the connection.
A comment line every 20 seconds keeps proxies from closing the connection.

### In the browser

`RealtimeProvider` (`src/lib/client/realtime.tsx`) owns the tab's single `EventSource`:

- An `app` event is parsed with `appEventSchema` (`@open-bot/domain`) and refreshes the procedures `APP_EVENT_REFRESHES` (`@open-bot/api`) names for it, plus the shell's state and Home, debounced by 120 ms.
  An event type the tab doesn't know only refreshes those two.
- A server that is stopping (SIGTERM, as on a deploy) ends every stream and turns new ones away with a closed connection, so tabs reconnect to the new deploy instead of staying on the old server until it is killed.
- A `ready` event names the deploy serving it.
  A tab whose code is from another deploy reloads (`apps/web/src/lib/client/deployment.ts`), or, while you're typing in a field, says so and reloads once you switch away.
  Composer drafts survive, since they are kept in local storage.
  A reload that brings back old code, as while the old and new servers both run, is tried again after 5 and then 30 seconds.
  After three tries, or when the tab can't keep count in session storage, it asks you to reload instead.
- A `ready` event refreshes the shell's state and Home.
  After the stream dropped, it also refreshes everything any event could have, because the events sent meanwhile are gone.
- A `notification` event fetches the notification and shows a toast, and an OS notification when allowed and the chat isn't already open.
- `run` events go to the chat that is watching. The provider remembers the last event id per chat and drops anything older, so a reconnect never applies an event twice.

`useChat` then folds events into the chat view with `applyRunEvent` from `@open-bot/domain`.
It's a pure reducer shared by the server (to build the first snapshot) and the client (to apply live events), so both always agree.
Events that arrive before the snapshot loads are buffered and applied after it, skipping any already included in the snapshot's cursor.

## The live screen

The computer panel embeds noVNC.
To connect, the browser asks `GET /api/desktop/token` for the worker's websocket URL and a token signed with `WORKER_SECRET` that expires in 60 seconds.
It then opens `wss://<worker>/vnc?screen=<id>&mode=view|control&token=...`.

The worker checks the token, and only allows `mode=control` while you hold that screen's lease.
See [Screens and takeover](/docs/flows/screens-and-takeover).

## Pages

| Route                        | What it shows                                                                                |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| `/`                          | Home: what each teammate finished or got stuck on, and what needs you.                       |
| `/chats/[chatId]`            | A chat, with the live timeline and the teammate's screen beside it.                          |
| `/bots/new`, `/bots/[botId]` | Creating and editing a teammate: job, memory, lessons, rules, automations, spending.         |
| `/computer`                  | Every screen, live, with takeover.                                                           |
| `/approvals`                 | The approvals inbox.                                                                         |
| `/automations`               | Schedules, page watches and webhooks, with their run history.                                |
| `/tasks`                     | The shared task board.                                                                       |
| `/skills`                    | Saved skills.                                                                                |
| `/vault`                     | Logins and cards.                                                                            |
| `/files`                     | A file browser for the computer's `/home/bot`.                                               |
| `/pages`, `/pages/[pageId]`  | The library of [pages](/docs/flows/pages), and one page in a sandboxed frame, with Ask.      |
| `/settings`                  | ChatGPT sign-in, the API key and cap, egress, Telegram, email, push, connections, About you. |

The app is installable: `manifest.ts` provides the web manifest, and `public/sw.js` is the service worker for push notifications.
