# Worker

`apps/worker` is an always-on Node 24 service.
It runs every teammate turn, serves every tool call, and owns every timer and long-lived connection in the system.

## Startup

`src/index.ts` wires everything together in a fixed order:

1. Parse the environment with zod (`src/env.ts`). Every value has a development default.
2. Open a Postgres pool and insert the single-row tables (`settings`, `computers`) if missing.
3. Build `ComputerClient` (botd), `CodexManager` (Codex through botd) and a shared `Context`: the env, the database, the logger, and a typed `EventEmitter` for in-process events.
4. Start the memory coordinator's background jobs (embedding and extraction).
5. Build every service, then `ToolHandlers`, then the `RunExecutor`.
6. **Recover**: mark every run still in `starting`, `running` or `waiting` as `interrupted`, with the error "The worker restarted while this was running". A Codex turn can't be resumed after its driver went away, so this is honest rather than optimistic.
7. Connect to botd's `/events` socket. When it opens, connect to Codex and start claiming runs. When Codex first reports a connection, write every saved skill to the computer.
8. Start the egress relay, push, phone notifications and Telegram, the account action executor, the scheduler, page watches, Gmail and Calendar triggers, and the email outbox sweep.
9. `LISTEN openbot_worker` on a dedicated connection, and start the HTTP server on `WORKER_PORT` (4001).

Whatever starts a timer, a listener, a socket or a background loop registers how to stop it with the `Runtime` (`src/core/runtime.ts`).
On `SIGTERM` or `SIGINT` it stops them all in reverse.
The server, the `LISTEN` connection and the timers are stopped first, then the triggers, the scheduler and the computer lifecycle.
Then account actions drain while push, phone notifications and Telegram still listen, and the egress relay, Codex, botd and the pool stop last (`src/shutdown.test.ts` pins the order of these stop calls).
Stopping a part doesn't wait for everything it started: the server isn't awaited until its last connection closes, and Telegram can still receive messages while account actions drain.

## Waking up

The worker reacts to three kinds of input:

| Input                   | Examples                                                                                                                      | Handled by                     |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| HTTP from the web app   | `POST /internal/messages/:id/dispatch`, `POST /internal/approvals/:id/decide`                                                 | `src/rpc/router.ts`            |
| `NOTIFY openbot_worker` | `runs`, `schedules`, `triggers`, `accounts`, `cancel`                                                                         | the listener in `src/index.ts` |
| Timers                  | the scheduler every 10 s, page watches and account triggers every 30 s, account actions every 30 s, a safety sweep every 15 s | each service                   |

The 15-second sweep calls `executor.pump()` and `processCancellations()`.
It catches anything that was queued while no one was listening, so a lost notification costs at most 15 seconds.

## The run executor

`RunExecutor` (`src/runs/executor.ts`) turns queued rows into running sessions.

### Claiming work

`pump()` is safe to call from anywhere, any number of times.
If a pump is already in progress, it sets a flag and runs one more pass when the current one finishes.
Each pass claims runs while there is spare capacity:

```sql title="The claim query"
update runs set status = 'starting'
where id = (
  select r.id from runs r
  where r.status = 'queued'
    and not exists (
      select 1 from runs a
      where a.chat_id = r.chat_id and a.bot_id = r.bot_id
        and a.status in ('starting', 'running', 'waiting')
    )
  order by r.created_at
  limit 1
  for update skip locked
)
returning id
```

Three properties come from this one statement:

- **Oldest first.** Runs start in the order they were queued.
- **One per teammate per chat.** A run waits while another run of the same teammate in the same chat is active, so a conversation is never processed out of order.
- **No double claims.** `FOR UPDATE SKIP LOCKED` makes concurrent claims skip a row another transaction holds.

The pass stops when `MAX_CONCURRENT_RUNS` sessions are executing.
When a session ends, it calls `pump()` again.

### Routing a message

`dispatchMessage(messageId)` decides who answers a message you sent:

- In a direct chat, the chat's teammate.
- In a group chat, the teammates you @-mentioned, or else the primary teammate, or else the first member.

For each target, if that teammate already has a session running in this chat and the message has no attachments, the message is **steered** into the running turn with Codex's `turn/steer`.
Otherwise a new run is queued with trigger `user`.

### Cancelling

Stopping a run sets `runs.cancel_requested_at` and sends `NOTIFY openbot_worker, 'cancel'`.
`processCancellations()` interrupts executing sessions with `turn/interrupt`, and marks queued runs `interrupted` directly.

## RunSession

A `RunSession` (`src/runs/session.ts`) executes one run.
It is covered step by step in [Life of a message](/docs/flows/chat-turn).
In short, it:

1. writes the teammate's workspace (`AGENTS.md`, skills, the memory pointer);
2. builds the prompt: the time, group chat context, memory, Always allow rules, the request and attachments;
3. picks the plan or the API key (see [Models and usage](/docs/flows/models-and-usage));
4. finds or creates the Codex thread (see [Agent runtime](/docs/architecture/agent-runtime#choosing-a-thread));
5. starts a turn, and maps every Codex notification to timeline items in `run_events`;
6. answers Codex's requests: dynamic tool calls, and approvals for commands and file changes;
7. on completion, writes the final status and reply, the usage ledger and notifications.

The `SessionRegistry` keeps executing sessions by run id and by chat and teammate.
Steering, approvals and takeovers use it to find a live session to deliver to.

### Writing events efficiently

`RunEventWriter` (`src/runs/events.ts`) is the only way a session writes events.

- Inserts go through a promise chain, so events are stored in the order they were written.
- Streamed text arrives as many small deltas. They are coalesced per item for up to **120 ms** and stored as one `delta` event, so a long answer becomes a handful of rows, not thousands.
- A non-delta event flushes pending deltas first, so order is preserved across types.
- After an insert, a `NOTIFY openbot_chat` is scheduled within **30 ms**, so bursts of events cause one notification.
- `drain()` waits for everything to be stored. The session calls it before writing the final run row, so a client that sees "completed" can read every event before it.

## Tool calls

When the model calls a dynamic tool, Codex sends an `item/tool/call` request.
`CodexManager` routes it by thread id to the session that owns the thread, which hands it to `ToolHandlers.handle()`.

The handler:

1. Checks that the teammate's **memory generation** hasn't changed since the run started. If it has, it interrupts the turn, so a teammate never acts on facts you just corrected.
2. Refuses tools a **swarm helper** may not use, like `notify_user` or `request_approval`.
3. Dispatches by name: desktop tools go to botd, tools in an integration's namespace (`gmail`, `calendar`, `notion`) to `AccountTools`, everything else to a service.
4. Records a rich timeline item itself (for example a desktop action with its screenshot), because the generic Codex item has less detail.
5. Returns `{ success, contentItems }`: text, or an image for desktop tools.

Desktop screenshots are stored as `artifacts` rows (JPEG bytes in Postgres), and the timeline item points to the artifact.
That is what makes frame-by-frame replay possible after the fact.

## Accounts

The worker serves your Gmail, Google Calendar and Notion to teammates.
The worker is the only process that decrypts their tokens, and makes every call to the providers.
What every integration shares is in `apps/worker/src/accounts/`; what is particular to each provider is in `packages/integrations`, one folder per provider.

| Part             | File                                                   | Responsibility                                                                                                                   |
| ---------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `AccountAccess`  | `apps/worker/src/accounts/access.ts`                   | Which connections a teammate may use, checking capabilities and granted scopes, tokens, and telling you once when a sign-in ends |
| `AccountTools`   | `apps/worker/src/accounts/tools.ts`                    | Routes each integration's tools to its adapter: checks access, runs reads, hands every change to the executor                    |
| `AccountActions` | `apps/worker/src/accounts/actions.ts`                  | The durable executor: claims, rechecks, runs, reconciles and reports every change, at most once                                  |
| Approvals        | `apps/worker/src/accounts/effects.ts`                  | `approvalFor()`, which decides from a change's effect whether it asks you                                                        |
| `Integrations`   | `packages/integrations/src/integration-registry.ts`    | One adapter per integration, its tool specs checked at start against the integration's definition in `@open-bot/domain`          |
| Gmail            | `packages/integrations/src/providers/google/gmail/`    | Gmail's REST API, building and freezing MIME, HTML to text                                                                       |
| Calendar         | `packages/integrations/src/providers/google/calendar/` | Calendar's REST API, time zones and free time, and each change's effect                                                          |
| Notion           | `packages/integrations/src/providers/notion/`          | An MCP client per account to Notion's hosted server, the curated tool list, and what counts as the teammates' own                |

Tokens come from `AccountStore` in `packages/integrations`, which refreshes under a row lock, so one refresh serves every caller in every process.
It refreshes each grant with the OAuth client that made it, so replacing your Google client doesn't break the sign-ins made with the old one.
A teammate names an account by its connection id, which its instructions list; a name works too when only one connection has it.
A read wraps its result as outside data and marks the run with `markReadOutsideData()`; from then on the run's `send_email`, outward actions and `create_webhook` ask you.

### The action executor

`AccountActions.submit()` records the frozen request and, when it needs you, its approval, in one transaction.
An action that needs nothing runs right away through the same path.
Otherwise the teammate waits up to 10 minutes for your decision, then carries on, and hears the outcome later.

The executor wakes on `NOTIFY openbot_worker, 'accounts'` (sent when you decide), every 30 seconds, and at start. Each sweep:

1. claims approved actions one at a time with a conditional update, so two workers can't both run one;
2. checks again that the connection is on with the same revision, the sign-in hasn't lost a permission or changed client since (the grant revision), the teammate still has it, and the capability is allowed and granted, or cancels the action with the reason;
3. runs it, and records `done`, `failed` for a clear refusal, or, when the answer was lost, asks the provider whether it happened;
4. reconciles actions still `executing` after their 5-minute lease, the same way, and marks one it can't settle `unknown`; when the provider says an action didn't happen, it checks everything in step 2 again before running it again;
5. polls Notion's background tasks every 15 seconds, for up to 15 minutes;
6. expires actions not decided within 7 days, closing their approvals;
7. reports each finished action once: its timeline item, and a follow-up run for anything but `done`.

### Adding an integration

Every integration is described once, and the rest of the app reads that description:

1. **The sign-in provider**, if it is new: its entry in `AUTH_PROVIDERS` in `packages/domain/src/integrations/accounts/` (label, base scopes, whether you paste in your own OAuth client or it registers one), and its `ProviderAdapter` in `packages/integrations/src/providers/` (authorization URL, token exchange, identity, refresh and revoke). A provider whose client you paste in also gets its setup steps in `apps/web/src/features/integrations/components/provider-guides.tsx`.
2. **The integration**: its definition next to the provider's, with its capabilities and the scopes each needs, its tools, any settings, and guidance for teammates. Settings, the connect dialog and teammates' instructions are drawn from it.
3. **Its adapter**: a class in its provider's folder in `packages/integrations/src/providers/` with the tool specs, `call()`, `probe()` for the connection test, and the runner for its changes, added to `ADAPTERS` in `packages/integrations/src/integration-registry.ts`.

The worker refuses to start when an integration has no adapter, or its tools differ from its definition.

## The internal HTTP API

`src/http.ts` is a plain `node:http` server.

- `GET /healthz` is open and returns `{ ok: true }`.
- Every other request needs the `x-worker-secret` header, compared in constant time.
- The routes are `workerContract` (`packages/api/src/worker/contract.ts`), served by oRPC's OpenAPI handler at fixed `/internal/...` paths, so a web app from the previous deploy can still call them.
- `src/rpc/router.ts` implements each procedure by calling services; rules about what is allowed live in the services, where the teammates' tools use them too.
- `src/rpc/handler.ts` runs around every procedure: one marked `wakesComputer` runs inside the lifecycle, so it wakes the computer and keeps it awake until it finishes, and whatever a procedure throws becomes a status and a message in `src/rpc/errors.ts`, the only place a service's error becomes a status.
  Every service's own error class extends `WorkerError` (`src/core/errors.ts`), which carries the status; a tool that throws one fails with its message (`src/tools/handlers.ts`), and anything else is logged as a fault.
- `PUT /internal/uploads/:id` streams raw bytes, so it is handled in `src/http.ts` outside the contract.
- Websocket upgrades on `/vnc` and `/egress/agent` (`src/ws.ts`) check a signed token from the query string instead.

The full list is in [Internal APIs](/docs/reference/http-api#the-worker).

## Logging

`src/logger.ts` writes one JSON object per line, with `time`, `level`, `scope` and `message`, plus fields.
Scopes nest, like `worker:computer` or `worker:run`.
An unhandled promise rejection is logged and doesn't crash the process, so one failing task can't take down every running teammate.
