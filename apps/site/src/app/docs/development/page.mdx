# Development

open-bot is a pnpm and Turborepo monorepo in strict TypeScript.
This page maps the repository, lists the checks and test suites, and collects the conventions that keep the parts consistent.

## Repository layout

```text
open-bot/
├── apps/
│   ├── web/          Next.js app: pages, server actions, read routes, the SSE stream, the phone's RPC
│   ├── worker/       Node service: runs, tools, services, the internal API, the egress relay
│   ├── botd/         The daemon inside the computer, bundled into the image
│   ├── desktop/      Electron shell and egress agent
│   ├── pages/        Serves published pages on an origin of their own
│   ├── mobile/       Expo Android app; setup and device tests in apps/mobile/README.md
│   └── site/         This site: the landing page, the tour and these docs
├── packages/
│   ├── db/           Drizzle schema, migrations, NOTIFY channels, the test database helper
│   ├── shared/       Types and pure logic shared by every app
│   ├── api/          Shared web/phone RPC contract and serializable views
│   ├── accounts/     OAuth flows and the token store for Google and Notion
│   ├── agent/        Codex app-server client and generated protocol types
│   ├── egress/       Tunnel framing, multiplexer, SOCKS server, agent
│   ├── page-kit/     The pages' styles, scripts, libraries, runtime and /page skill
│   └── memory/       The memory service and its background jobs
├── images/computer/  The computer's Dockerfile and its filesystem overlay
├── e2e/              Playwright end-to-end tests for the whole stack, and stand-ins
├── tools/showcase/   Typed demo data and screenshots for UI review
├── scripts/          test/ runners, check/ repository checks, ops/ and dev/ tools
└── docker-compose.yml  Postgres and the computer for local development
```

Workspace packages export TypeScript source, not built JavaScript.
The web app compiles them through Next.js, the worker, botd and pages bundle them with esbuild, and tests run them directly.
Every app and package has an `AGENTS.md` with its entry points, invariants and tests.

## Commands

| Command                               | What it does                                                                            |
| ------------------------------------- | --------------------------------------------------------------------------------------- |
| `pnpm dev`                            | The web app, the worker and the pages service, with reload                              |
| `pnpm infra:up`                       | Postgres and the computer in Docker, waiting until healthy                              |
| `pnpm computer:build`                 | Rebuilds the computer image (after changing botd or the image)                          |
| `pnpm db:migrate`, `pnpm db:generate` | Apply migrations, or generate one from the schema                                       |
| `pnpm lint`                           | ESLint over the repository, with no warnings allowed                                    |
| `pnpm format`, `pnpm format:check`    | Prettier                                                                                |
| `pnpm typecheck`                      | `tsc` in every package (and `next typegen` for the Next.js apps)                        |
| `pnpm test`                           | Vitest unit tests in every package                                                      |
| `pnpm verify`                         | Lint, the doc path and vocabulary checks, typecheck, unit, script and integration tests |
| `pnpm verify:affected`                | The same, limited to what changed since `main`                                          |

### Unit tests

Vitest, next to the code they test (`*.test.ts`).
The pure logic in `@open-bot/shared` is covered most: approval rules, schedules, page diffing, the timeline reducer, templates, vault and budgets, connections, email parsing, Telegram formatting, model access and pricing.
The worker and botd test their trickiest parts directly: the lease, the cookie jar's merge rules, the Codex client, the event mapper, instructions and push payloads.
`packages/egress` has contract tests for the framing, flow control and SOCKS, and writes the test vectors the Kotlin core reads (`pnpm --filter @open-bot/egress vectors`).

### Integration tests

`pnpm test:integration` runs every `*.integration.test.ts` against real Postgres: teammate management, the phone API, uploads, pages, account sign-ins, actions and triggers, screen operations and memory.
Each suite creates its own fresh database on the server named by `TEST_DATABASE_URL`, applies every migration, and drops it afterwards (`@open-bot/db/testing`), so suites run in parallel.
Without `TEST_DATABASE_URL`, the command starts a throwaway pgvector container (`scripts/test/pg.sh`) and removes it when it finishes.
CI runs them against a Postgres service; there a missing `TEST_DATABASE_URL` fails the run instead of skipping.

### The memory suite

`pnpm test:memory -- --e2e` creates its own pgvector container, applies every migration, runs database and provider tests against a deterministic local HTTP server, smoke-tests the compiled worker, and exercises the memory UI at desktop and phone widths.
It removes only its own container.

### End-to-end tests

Playwright drives the real stack: start it with `pnpm infra:up` and `pnpm dev`, then:

```sh title="Terminal"
E2E_EMAIL=you@example.com E2E_PASSWORD=… pnpm e2e --grep-invert @agent   # fast
E2E_EMAIL=you@example.com E2E_PASSWORD=… pnpm e2e --grep @agent          # real teammates at work
```

- A `setup` project signs in once and saves the session to `e2e/.auth/owner.json`.
- Tests tagged `@agent` run real turns on the computer, take minutes, and use your ChatGPT plan.
- Tests run serially (`workers: 1`), because they share one computer and one database.
- `e2e/global-teardown.ts` deletes test teammates by a name pattern. New test name prefixes must be added to it.

Stand-ins replace outside services, so the default run needs no outside account:

| Stand-in                               | Replaces                                                       | Used with                                                               |
| -------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `e2e/telegram-mock.ts` (port 4797)     | The Telegram Bot API                                           | `TELEGRAM_API_BASE_URL`, `E2E_TELEGRAM=1`                               |
| `e2e/accounts-stand-in.ts` (port 4796) | Google sign-in, Gmail, Google Calendar and Notion's MCP server | `GOOGLE_BASE_URL`, `NOTION_MCP_URL`, `E2E_ACCOUNTS=1`                   |
| The plan rehearsal mock (port 4799)    | ChatGPT and the OpenAI API, answering like an exhausted plan   | `OPEN_BOT_PLAN_BASE_URL`, `OPENAI_API_BASE_URL`, `E2E_PLAN_REHEARSAL=1` |
| `e2e/mcp-stand-in.ts`                  | An MCP server                                                  | Connection tests                                                        |
| `e2e/job-scout-stand-ins.ts`           | Job portals and a tracker                                      | Job Scout and the apply guard                                           |
| A plain-HTTP push service              | Web Push endpoints                                             | Push tests                                                              |

Two kinds of test do use real accounts, and both are opt-in:

- `@agent` tests use your ChatGPT plan.
- One Job Scout test files postings into a real Application tracker. It runs only with `E2E_TRACKER_MCP_URL` and `E2E_TRACKER_TOKEN` set.

To run the suites that need a stand-in, start the services pointed at it:

```sh title="Telegram"
TELEGRAM_API_BASE_URL=http://127.0.0.1:4797 pnpm --filter @open-bot/worker dev
E2E_TELEGRAM=1 E2E_EMAIL=you@example.com E2E_PASSWORD=… pnpm e2e --grep Telegram
```

```sh title="Accounts (with no accounts connected)"
GOOGLE_BASE_URL=http://127.0.0.1:4796 NOTION_MCP_URL=http://127.0.0.1:4796/mcp pnpm dev
E2E_ACCOUNTS=1 E2E_EMAIL=you@example.com E2E_PASSWORD=… pnpm e2e e2e/accounts.spec.ts
```

```sh title="Plan fallback"
OPEN_BOT_PLAN_BASE_URL=http://host.docker.internal:4799/plan OPENAI_API_BASE_URL=http://host.docker.internal:4799/api pnpm --filter @open-bot/worker dev
E2E_PLAN_REHEARSAL=1 E2E_EMAIL=you@example.com E2E_PASSWORD=… pnpm e2e --grep rehearsal
```

Every variable the tests read is listed in [Configuration](/docs/reference/configuration).

### Self-contained runners

These start their own throwaway containers and never touch your app database or your computer:

- `pnpm test:pocket-inbox` runs the pocket inbox Playwright spec against its own database and web server, with no worker, model or device.
- `pnpm test:owner-reset` runs the owner password reset command (`scripts/ops/owner-reset-password.mjs`) end to end.
- `pnpm test:computer-sleep` runs a real computer container, Postgres and the built worker in their own containers, and checks that the computer goes idle, keeps its browser state across sleep, and wakes for work. It needs the computer image (`pnpm computer:build`).

### The Android app

`pnpm test:mobile-ui` runs the Maestro flows on a device or emulator with the development build.
Its setup, variables and the notification tests are in `apps/mobile/README.md`.
The app's unit tests run with `pnpm --filter @open-bot/mobile test`, and its Kotlin tunnel core with `./gradlew test` in `apps/mobile/modules/egress/core`.

### This site

```sh title="Terminal"
pnpm --filter @open-bot/site dev        # http://localhost:3200
pnpm --filter @open-bot/site test:e2e   # builds and serves it the way it is deployed
```

The end-to-end run needs the encoded tour first (`pnpm --filter @open-bot/site media:encode`).
`pnpm typecheck` covers this site, and Cloudflare builds it on every pull request.

## Conventions

These are easy to miss and cost time when forgotten.

### Agent and protocol

- **Bump `TOOLS_VERSION`** (`apps/worker/src/tools/definitions.ts`) whenever you change a tool or `DEVELOPER_INSTRUCTIONS`. Threads keep the tools they started with, and the bump makes the next run of every chat start a fresh thread.
- **Regenerate the protocol** after changing `CODEX_VERSION` in the image: `pnpm --filter @open-bot/agent generate:protocol`, then fix any type errors in the `Methods` map.
- **Never block a tool for long.** Codex hands control back to the model after about 30 seconds. Anything that waits on the user must be decidable after the run ends (see the email outbox).
- **Unwrap shell commands** with `shellScript()` before showing or matching them. Codex wraps every command in `/bin/bash -lc '...'`.

### Data and events

- **Write run events through `RunEventWriter`** or `appendRunEvent()`, never with a raw insert, so ordering and notifications stay correct.
- **Publish an `AppEvent`** after any change the UI shows, so open tabs refetch.
- **Treat `NOTIFY` as a hint.** Read the rows, and make sure a periodic sweep would eventually catch up.
- **Memory goes through `@open-bot/memory`.** Never write `settings.about_me` or `lessons` directly; they are projections.

### Web app

- **Browser reads use `GET` routes.** Next.js runs server actions one at a time per client, so reads done as actions queue behind each other. The phone's RPC and upload entry points are documented in [Internal APIs](/docs/reference/http-api#writes-and-the-phone-api).
- **Hydration errors fail tests.** E2E specs import `test` from `e2e/fixtures.ts`, which fails any test whose page logs a hydration error. Relative times from server data use the `TimeAgo` component.

### The computer

- **Rebuild the image after changing botd**, `packages/egress` or `images/computer`: `pnpm computer:build && docker compose up -d --wait computer`.
- **Keep the user split.** Anything that touches a display runs as `desktop` through botd. Nothing in the `bot` user's reach may get display access.
