# Internal APIs

open-bot's processes talk over a few small HTTP and websocket APIs.
None of them is a public, stable API: they change together with the code.
This page lists them, so you can find where any request is handled.

## The web app

### Public endpoints

| Method and path                          | Auth        | Purpose                                                                 |
| ---------------------------------------- | ----------- | ----------------------------------------------------------------------- |
| `GET`, `POST`, `PUT` `/api/hooks/:token` | The token   | A teammate's webhook. Body up to 256 KB. Returns `202` with the run id. |
| `POST /api/inbound/email/:token`         | The token   | Postmark's inbound email webhook                                        |
| `/api/auth/*`                            | Better Auth | Sign-in, sign-up (owner only), passkeys, sessions                       |

### The API

The browser and the Android app read through one typed API, the oRPC contract in `packages/api/src/contract.ts`, served at `/api/rpc/*` by `apps/web/src/lib/server/api/router.ts`.
Its procedures, inputs, outputs and errors are the authoritative reference; the view schemas sit next to it in `packages/api/src` (`views.ts`, `home.ts`, `automations.ts`, ...).
Every procedure needs the owner's session, and browsers may only call it from the app's own pages.
The server validates every output against its schema, so a query that drifts from its view fails loudly instead of handing the client the wrong shape.

| Namespace                                          | Reads                                                                      |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| `app.state`                                        | The web app shell's state: teammates, chats, skills, the computer, badges  |
| `home.get`                                         | What needs you, recent work, and what finished since you were last here    |
| `chats`, `teammates`, `approvals`, `notifications` | Chats and their messages, teammates' lessons and spending, the inbox       |
| `schedules`, `triggers`                            | Automations and their recent runs                                          |
| `tasks`, `skills`, `vault`, `memory`, `profile`    | Each page's data; memory with its history and what a reply was given       |
| `connections`, `accounts`, `email`, `telegram`     | Integrations, and how to set them up                                       |
| `push`, `settings`                                 | Push status, usage, the API key fallback, plan limits                      |
| `pages`, `search`, `files`, `screens`              | The page library, ⌘K search, the computer's files, screens and last frames |

`files.list`, `telegram.status`, `push.status` and `settings.rateLimits` ask the worker, and fail with status 503 while it can't be reached, which the browser shows as offline.

### Files, streams and tokens

The remaining routes need the owner's session too.
They stay plain HTTP because they stream or return bytes:

| Path                                                 | Returns                                                                     |
| ---------------------------------------------------- | --------------------------------------------------------------------------- |
| `GET /api/stream?chat=&after=`                       | Server-sent events (see [Web app](/docs/architecture/web-app#live-updates)) |
| `GET /api/artifacts/:id`                             | A screenshot or upload                                                      |
| `GET /api/bots/:id/export`                           | A teammate as an export file                                                |
| `GET /api/memory?botId=`                             | Memory as a Markdown file                                                   |
| `GET /api/pages/versions/:id/thumbnail`, `/download` | A version's thumbnail, and its HTML as a download                           |
| `GET /api/files/download`                            | A file from the computer under `/home/bot`                                  |
| `GET /api/desktop/token`                             | A 60-second VNC token and the worker's websocket URL                        |
| `GET /api/desktop/egress-token`                      | A 120-second egress token and URL, for the desktop app                      |

The JSON reads these procedures replaced, such as `GET /api/state`, answer 401 until 2026-12-01 (`apps/web/src/lib/retired-routes.ts`).
A tab still running code from before sends itself to sign in on a 401, which takes a signed-in owner home on current code.

### Writes

Chats, messages, runs and feedback, approvals, screens, pages, notifications and the egress mode are written through the API, by the browser and the Android app alike.
The browser's other writes are still server actions in `apps/web/src/lib/actions.ts`, until they move to the API.
Both use the services in `apps/web/src/lib/server/api/`.
In the browser, `attempt()` in `apps/web/src/lib/client/mutate.ts` turns a call into `{ ok, data }` or `{ ok, error }` with the server's own message.
Input a procedure refuses answers 400 with its schema's messages, such as "Name the chat.", and the zod issues in `data.issues`.

Browsers may only write from the app's own pages.
`crossSiteRefusal()` in `apps/web/src/lib/server/origin.ts` answers 403 to a write whose `Origin` is another site, for the API and every `authed()` route; a request with no `Origin`, from the phone, may write.
The API answers a GET only for a procedure whose route says GET, and none does, so a link or image on another site can never reach a write.
`apps/web/src/app/api/routes.test.ts` fails when a route that takes writes skips that check without saying why.

`PUT /api/uploads/:uploadId` accepts raw attachment bytes with the owner's session.
The browser and the phone upload the same way, with `uploadWithRetries` in `packages/api/src/uploads.ts`: one id for every attempt, and before sending again it asks `uploads.status` whether the last attempt arrived.
The metadata headers are `UPLOAD_HEADERS` in the same file; see [Saving the message](/docs/flows/chat-turn#saving-the-message) for attachment acceptance and cleanup.

## The worker

Base URL `WORKER_URL` (port 4001).
Every route except `/healthz` requires `x-worker-secret: <WORKER_SECRET>`.
Bodies and responses are JSON, except upload request bodies, which are raw bytes.

The routes below are one typed contract, `workerContract` in `packages/api/src/worker/contract.ts`, with each procedure's path, input and output schemas.
The worker implements it in `apps/worker/src/rpc/router.ts`, and the web app calls it with the typed client in `apps/web/src/lib/server/worker.ts`, so changing a response is a type error in the web app.
A procedure's input is its path parameters merged with the JSON body, or with the query string for `GET`.
Errors are `{ error, code }` with the HTTP status, and `error` is a message the web app can show.

Procedures marked `wakesComputer` in the contract wake a sleeping computer first, and keep it awake until they finish; in the tables below, they are marked with ☀.
A request the web app gives up on stops waiting for the computer.
Reading status never wakes it.

The paths are a contract between deployed versions too: Railway deploys the web app and the worker separately, so for a few minutes either can be older.
A path or input field is removed only once no deployed web app calls it.

## botd

Base URL `BOTD_URL` (port 7000, private).
Every route except `/healthz` requires `Authorization: Bearer <BOTD_TOKEN>`, or `?token=` on websockets.
The routes are `botdContract` in `packages/api/src/botd/contract.ts`, an oRPC contract with the request and answer schema of each.
botd (`apps/botd/src/router.ts`) checks every request against it and answers `400` for one that doesn't fit; the worker (`ComputerClient` in `apps/worker/src/computer.ts`) checks every answer and every event.
Errors are `{ error, code }` with the status: `400` bad input, `401` no token, `409` refused for now, `500` failed.
Routes marked ☀ work on the computer: the worker wakes the computer for them, and botd counts them as activity until they finish, so it can't quiesce under them.

| Route                           | Purpose                                                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `GET /healthz`                  | Liveness, unauthenticated; `503` while the computer is unhealthy, unless the lifecycle manages it            |
| `GET /health`                   | `ComputerHealth`: Codex state, screens with leases, egress                                                   |
| `GET /lifecycle/capabilities`   | `{ version, enabled, phase? }`: whether botd's sleep state machine is on                                     |
| `POST /lifecycle/lease`         | `{ owner, demand }`: claim the lifecycle and say how much work the worker has                                |
| `POST /lifecycle/ensure`        | `{ owner }`: start what was stopped for sleep                                                                |
| `POST /lifecycle/quiesce`       | `{ owner }`: stop everything so the computer can sleep; `409` while work still runs                          |
| `POST /computer/action` ☀       | `{ run, action }`: perform a desktop action and return a screenshot, the pointer, and any apply guard blocks |
| `POST /computer/read` ☀         | `{ run, selector? }`: the front page's text and links                                                        |
| `POST /computer/fill` ☀         | `{ run, secret, site }`: type a vault secret, after checking the site                                        |
| `POST /computer/code-context` ☀ | `{ screenId }`: the site of the focused field, before a one-time code is typed                               |
| `POST /computer/type` ☀         | `{ screenId, takeoverId, operationId, expectedSite, pressEnter, text }`: type a one-time code                |
| `POST /screens/start` ☀         | Start a screen without using it                                                                              |
| `POST /screens/forget` ☀        | Stop a screen and delete its profile                                                                         |
| `POST /lease/run/release` ☀     | Release a run's lease when it ends                                                                           |
| `POST /lease/user/take` ☀       | Give you a screen's lease, preempting a run; `409` while a code is being typed                               |
| `POST /lease/user/release` ☀    | Release your lease (`handed_back`, `user_idle`, `user_disconnected`)                                         |
| `POST /lease/user/touch` ☀      | Record your input                                                                                            |
| `POST /pages/check` ☀           | `{ path }`: check a page in a headless browser; see [The checker](/docs/architecture/pages#the-checker)      |

Errors from `/computer/fill` and `/computer/type` never repeat their input, which carries a secret.

| Websocket            | Purpose                                                |
| -------------------- | ------------------------------------------------------ |
| `/events`            | `lease` and `health` events, pushed to the worker      |
| `/codex`             | A bridge to `codex app-server` on `127.0.0.1:4500`     |
| `/egress`            | The computer's end of the egress tunnel                |
| `/vnc?screen=&mode=` | A bridge to a screen's view-only or control VNC server |

botd also serves drafts of pages on `127.0.0.1:7080`, for the computer's own browsers only; see [The preview server](/docs/architecture/pages#the-preview-server).

### Action errors

`/computer/action`, `/computer/read` and `/computer/fill` answer `200` with `{ ok: false, code, message }` when they can't do what the teammate asked, and the message goes to the model as the tool's result:

| Code               | Meaning                                                               |
| ------------------ | --------------------------------------------------------------------- |
| `user_has_control` | You hold the screen, or took it during the action                     |
| `desktop_busy`     | Another run of the same teammate holds the screen, after waiting 30 s |
| `invalid_action`   | There was no secret to fill, or it was too long                       |
| `wrong_site`       | A vault login didn't match every visible page                         |
| `failed`           | Anything else, like a screen that couldn't start                      |

## The pages service

Base URL `PAGES_URL` (port 3400, public, on its own origin).
It has no session: a version opens only with a key the web app signed.
See [The pages service](/docs/architecture/pages).

| Route                              | Purpose                                                                                            |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| `GET /healthz`                     | Liveness                                                                                           |
| `GET /lib/*`                       | The page kit and libraries, cacheable, readable from any origin                                    |
| `GET /v/:versionId?k=&theme=&ask=` | One version with the runtime added. `403` for a missing, wrong or expired key; `404` once deleted. |

It answers only `GET` and `HEAD`.

## Codex app-server

The worker speaks JSON-RPC 2.0 to Codex through botd's `/codex` bridge.
The methods and server requests open-bot uses are listed on [Agent runtime](/docs/architecture/agent-runtime#methods-open-bot-uses).
