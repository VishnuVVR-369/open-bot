# Security model

open-bot gives AI agents a real computer, your sign-ins, and sometimes your card.
This page describes what protects what, the credential on every connection, and the risks that remain.
The known risks were reproduced in the `computer` image, not inferred from reading code.

## Assumptions

- **One owner.** Every teammate works for the same person, and the app has exactly one account.
- **Teammates are trusted, but not blindly.** They follow instructions, but the pages and emails they read may try to steer them. Consequential actions go through approvals that the teammate can't skip.
- **The computer is the sandbox.** Codex's own sandbox is off. The container, the Linux users inside it, and botd's checks are the boundaries.

| Connection                               | Credential                                                                  | Lifetime                                 |
| ---------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------- |
| Browser to web app                       | Better Auth session cookie, owner only                                      | 30 days, refreshed daily                 |
| Browser to worker `/vnc`                 | HMAC-SHA256 token, purpose `vnc`, signed with `WORKER_SECRET`               | 60 seconds                               |
| Desktop app to worker `/egress/agent`    | HMAC token, purpose `egress`                                                | 120 seconds                              |
| Web app to worker `/internal/*`          | `x-worker-secret` header, compared in constant time                         | Static secret                            |
| Computer to worker `/model-proxy/*`      | `HMAC(ENCRYPTION_KEY, "model-proxy")` in the URL, compared in constant time | Static, changes with `ENCRYPTION_KEY`    |
| Worker to botd                           | `Bearer BOTD_TOKEN` (header or query)                                       | Static secret                            |
| Anyone to a webhook                      | The random token in the URL                                                 | Until you rotate it                      |
| Postmark to inbound email                | The random secret in the URL                                                | Until you change it                      |
| Browser to the pages service             | HMAC-SHA256 key for one version, signed with `PAGES_SECRET`                 | 10 minutes                               |
| Worker to Google and Notion              | Your OAuth access token, refreshed by the worker                            | About an hour (Google), 8 hours (Notion) |
| Google or Notion to the sign-in callback | A one-time `state`, bound to your session, and a PKCE verifier              | 10 minutes                               |

Tokens for websockets exist because a websocket from the browser can't carry the session cookie to the worker's different origin.
The web app issues them only to a signed-in session, and they say what they're for, so a VNC token can't open the egress tunnel.

## Authentication

- `OWNER_EMAIL` is the only email that can create an account, and only one account can exist. Both are enforced in a database hook, before the user row is written.
- Passwords are at least 10 characters. Passkeys are supported.
- Every page, API procedure and route checks the session on the server. The middleware redirect is only a convenience.
- The page to return to after signing in (`/login?next=...`) can't send you to another site. `safeNext()` (`apps/web/src/lib/sign-in-return.ts`) accepts only a path on the app's own origin, refuses `//host`, `/\host`, any scheme, control characters (also once percent-decoded), and `/login`, `/setup` and `/api`, and answers `/` for anything else.
- A write sent from another site's page is refused before it runs: the API and `authed()` routes answer 403 to a foreign `Origin` (`crossSiteRefusal()` in `apps/web/src/lib/server/origin.ts`), and the API runs no procedure for a GET.

## Secrets at rest

`ENCRYPTION_KEY` (32 random bytes, base64) encrypts every secret in Postgres with AES-256-GCM, with a random IV per value and an authentication tag that detects tampering:

- the OpenAI API key, the Telegram bot token and the VAPID private key (`credentials`);
- vault logins and cards (`vault_items`);
- MCP connection headers and environment variables (`connections`);
- your Google OAuth client's secret (`oauth_clients`), and the tokens of your Gmail, Calendar and Notion accounts (`account_connections`).

The web app encrypts when you save, and the worker decrypts only at the moment of use.
Losing `ENCRYPTION_KEY` makes these unreadable, so back it up with the database.

The OpenAI API key never reaches the computer.
Codex's API key provider points at the worker's [model proxy](/docs/architecture/agent-runtime#the-model-proxy), and the worker adds the key to each request itself, so the key never reaches the computer; with `MODEL_PROXY=off` the key isn't used at all.

The ChatGPT login is not in Postgres.
In development, only a short-lived access token is passed to the computer, and the refresh token stays on your machine.
In the cloud, Codex keeps its login in `/home/bot/.codex` on the computer's volume, readable only by the `bot` user.
Plan requests go through the model proxy with that login in their headers: the worker passes it on to ChatGPT unchanged and never keeps it.

## Inside the computer

| Protection                                 | How                                                                                                                                             |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Teammates can't drive the desktop directly | Codex and its shell run as `bot`, which can't read any display's X auth cookie. Desktop actions go through botd.                                |
| You always win the screen                  | botd's lease: taking over preempts the run and kills its in-flight input. While you hold it, the teammate's desktop tools and screenshots fail. |
| Only botd can drive a browser              | Chromium uses `--remote-debugging-pipe`. No DevTools port is open.                                                                              |
| Sign-ins are guarded                       | The shared cookie jar is in `/home/.botd`, readable only by root.                                                                               |
| Vault secrets don't leak through processes | botd types them through `xdotool`'s stdin, and a login only fills on its own site.                                                              |
| No job applications                        | The apply guard fails submissions to job portals unless you hold the screen.                                                                    |
| The computer isn't on the internet         | botd listens on port 7000 on the private network only. VNC and Codex listen on localhost.                                                       |

## Model logs

The worker logs every model request that goes through the model proxy and every memory AI request, in the `model_*` tables.
It also logs every message between itself and Codex, in `codex_events`, and the turns of each run, in `run_turns` (see [Data](/docs/architecture/data#model-logs)).

- **What they hold.** Requests and responses are stored as sent: your messages, what teammates read and wrote, tool calls and their output, and the model's encrypted reasoning.
  Treat them like the rest of the database.
  Only the owner can read them, in Settings, Model logs (see [Data](/docs/architecture/data#where-they-are-shown)); every procedure that serves them needs the owner's session.
  So does the JSONL export, which holds the requests in full, as stored; a file you download is yours to keep safe.
- **How long they are kept.** Forever, unless you choose a window under Settings, Model logs, Retention.
  Then a daily sweep removes the bodies of older requests and Codex messages, including any text in a request's parameters, and keeps their numbers, statuses and tool names (see [Data](/docs/architecture/data#retention)).
- **What they never hold.** Headers that carry a credential (authorization, cookies, API keys, tokens, secrets) are dropped before anything is saved, so neither your API key nor the computer's ChatGPT token reaches the logs on their way to the model.
  They can still be in a request's content if a teammate read them and showed them to the model (see below).
  The same headers are dropped from the header objects the model sends back in its events and errors; exactly what that covers, and what it doesn't, is under [Data](/docs/architecture/data#model-logs).
  The `chatgpt-account-id` header, which names your ChatGPT account, is dropped the same way.
  A memory AI request keeps only its `content-type` header, and its endpoint without credentials, query or fragment.
- **What `codex_events` holds.** Each message's method, its thread, turn and item, and its payload: your messages and each turn's input, the items Codex streamed (commands with their output, file changes with their diffs, MCP and open-bot tool calls with their results), approvals, thread settings, and file contents' sizes.
  Streaming deltas are only counted, since the completed item holds their content.
- **What is redacted in `codex_events`.** Every payload is redacted before it is queued (`redactCodexPayload` in `@open-bot/domain`), by method, by key, by credentials file and by pattern:
  - the sign-in messages (`account/login/start`, the `account/chatgptAuthTokens/refresh` request and the worker's answer to it, `getAuthStatus`) keep only their `type`, `reason` and plan type, so the ChatGPT tokens Codex is given or asks for are never stored;
  - any key that names a credential (`authorization`, `token` or any key ending in token, `access_token`, `refresh_token`, `api_key`, `apiKey`, `secret`, `password`, `passwd`, `passphrase`, `bearer`, `cookie`, `credential`, `private_key`, `signature`, `account_id`, and `auth` or `pass` as whole keys) has its value redacted, at any depth;
  - every value of an `env`, `headers`, `http_headers` or `env_http_headers` map is redacted, with its names kept, which covers MCP servers' and model providers' headers and environment in the `config` of `thread/start`, `thread/fork` and `thread/resume`;
  - an MCP server's `url` keeps only its origin;
  - a command, file read or file change that names a known credentials file (`.codex/auth.json`, `.netrc`, `.git-credentials`, `.pgpass`, `.npmrc`, `.pypirc`, `.aws/credentials` and `.aws/config`, `.config/gcloud/`, `.azure/`, `.docker/config.json`, `.kube/config`, `.config/gh/hosts.yml`, `.ssh/id_*`, `.gnupg/`, `.env` files) keeps only what it is and the files it names: its command text, output, diff and content are replaced whole, since a command can hold what it writes;
  - in every string (`redactSecretText`), these are redacted:
    - the model proxy's token, JWTs, PEM private keys (to their end line, or to the end of a cut string), and `Bearer` and `Basic` credentials;
    - API keys and tokens with a known prefix: `sk-` (OpenAI, Anthropic), Stripe `sk_`/`rk_` live and test keys, GitHub `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_` and `github_pat_`, GitLab `glpat-`, Slack `xox*-`, Google `AIza`, npm `npm_`, and AWS `AKIA`/`ASIA` access key ids;
    - a URL's user and password (`https://alice:secret@host`, `postgres://...`, `https://token@github.com`), in any scheme written with `://`;
    - the whole value of a header or `name: value` line whose name is like the keys above (`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, `password:` in YAML): every cookie and an authorization's scheme and parameters, up to the quote the header was opened with (`-H "Cookie: a=1; b=2"`, also escaped in a JSON string) or the end of its line;
    - `.netrc` entries' `login`, `password` and `account` values, whether the entry is on one line or spread over several, once the text has a `machine <host>` or `default` entry;
    - a command-line flag named like the keys above (`--password x`, `--api-key=x`, `--token 'x'`), and a user with a password after `-u`, `--user` or `--proxy-user` (`curl -u alice:secret`);
    - a credential written under a name like the keys above as JSON (`"refresh_token": "..."`, also escaped inside another JSON string), as `key=value` (env files, query strings, shell with any quoting: `'..'`, `".."`, `$'..'`, `$".."`, also when the string was cut inside the quote) or as `key: value`;
  - file contents read or written through Codex (`dataBase64`) are stored only as their size, and any string past 1 MiB is cut.
- **What is guaranteed.** No value is stored in `codex_events` under a key that names a credential, in a header or env map, in a sign-in message, or in the command, output or content of anything that names a credentials file above.
  No string keeps a JWT, a PEM private key, a key or token with one of the prefixes above, URL userinfo, the value of a credential header, a `.netrc` login or password, or a credential assigned to such a name in one of the forms above.
- **What is not covered.** Redaction errs on the side of removing more: text that only looks like a credential (`password: see the docs`, a `default login` in prose) loses its value too.
  A credential written in none of these ways is stored as it came:
  - an opaque token or password on its own, in prose, or as a command's output (`echo $TOKEN`, a password printed by a script);
  - a value under a name that doesn't say what it is (`key=...`, `pwd=...`, `DATABASE=...`), or in a format other than those above, such as a `.pgpass` line (`host:port:db:user:password`) outside that file;
  - a password given as a short flag other than `-u` (`mysql -pSECRET`, `sshpass -p secret`), or as a command's positional argument;
  - a credential split across several strings, encoded (base64, hex), or inside a `.netrc` `macdef` body;
  - a URL's userinfo with no `://` (`user:pass@host` on its own), and a password with an unescaped `/`, `?` or `#` in it;
  - the contents of a credentials file not on the list above.
- **What the model logs hold besides.** Model requests and their items (`model_requests`, `model_blobs`) are stored as Codex sent them, so whatever a teammate read and showed the model is there too, credentials included; only headers are stripped from them.
  The ChatGPT and API key tokens the worker and Codex use are never in either table, since they travel only in headers and in the sign-in messages above.
- **Who reaches the proxy.** Its URL carries a token derived from `ENCRYPTION_KEY`, which keeps the rest of the private network (web, pages) out.
  Teammates run as `bot`, the user Codex runs as, so they can read the URL from Codex's thread config; that grants nothing more.
  The proxy only forwards to fixed upstreams, chosen by route, and adds the API key only for a thread with a live run on the key, which already passed the monthly cap check.
  On the plan route it adds nothing: a request carries the computer's own ChatGPT login, as it would going straight to ChatGPT.
  When `OPEN_BOT_PLAN_BASE_URL` points the plan route at a rehearsal's stand-in, the proxy replaces every credential and the account header, so a stand-in never sees a real login.
- **Who reads them.** Nothing reads them yet; teammates have no access to them.

## Outside the computer

- **Page watches** fetch from the worker and refuse private, loopback and metadata addresses in production (`WATCH_ALLOW_PRIVATE_URLS=false`), at every redirect.
- **The egress agent** refuses any destination whose name resolves to a private or local address, and connects to the checked address to defeat DNS rebinding. A teammate can't reach your home network.
- **Webhooks** are rate limited to 30 runs an hour each, and bodies to 256 KB.
- **Prompt injection.** Watched pages, webhook payloads, emails, `browser_read_page` results and everything read from your accounts are wrapped in notes that mark them as outside data. That reduces the risk but can't remove it, which is why approvals and budgets don't depend on the model's judgment.

## Your accounts

[Gmail, Google Calendar and Notion](/docs/flows/accounts) let teammates act as you, and what they read there was written by anyone who can email you, invite you or share a page.

| Protection                          | How                                                                                                                                                                                                  |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Teammates never hold your tokens    | Tokens are encrypted in Postgres and used only by the worker, which makes every provider call. Nothing reaches Codex's config, the computer, or a teammate's shell.                                  |
| Only what you allowed               | The app asks Google only for the scopes of the switches you turned on, and the worker checks the connection, the teammate's access, the switch and the granted scope on every call.                  |
| A sign-in can't be swapped          | Each sign-in uses PKCE and a one-time state bound to your session. A reconnect that comes back as a different Google account or Notion workspace is refused.                                         |
| Anything others see asks you        | The worker classes every change from its arguments, and sending, invitations and Notion changes others see always ask, with no Always allow. When it can't tell, it asks.                            |
| What you approve is what runs       | The exact request is frozen when it is asked for, so a draft edited later doesn't change what is sent, and an event changed since fails.                                                             |
| At most once                        | The action executor claims each action atomically, rechecks the connection before running it, and never repeats an action whose answer was lost: it looks at the account, or tells you to check.     |
| Reading your accounts locks sending | Once a run reads anything from your accounts, emails, actions others see and new webhooks ask you whatever the teammate's autonomy, and so do runs it starts and runs that mail or an event started. |
| Outside data stays data             | Reads are wrapped as outside data that can't close its own wrapper, and hidden text in emails is dropped.                                                                                            |
| Notion stays in the workspace       | Notion's sign-in reaches everything you can see in the workspace. Teammates can only fetch Notion pages and databases, search in the workspace only, and results from connected sources are dropped. |

<Callout kind="risk" title="The shell can still reach the internet">
  These protections cover what the app sends for teammates. A teammate's shell has network access,
  so a teammate that an email talked into it could post what it read with `curl`. Closing that gap
  is the egress rule in [risk 4](#4-egress-is-a-browser-setting-not-a-network-rule), extended to the
  `bot` user. Until then, give your accounts only to teammates whose job needs them, and keep
  **Always ask before acting for me** on.
</Callout>

## Pages

A [page](/docs/flows/pages) is HTML a teammate wrote, often from websites it read, so it's treated as untrusted code.
[The pages service](/docs/architecture/pages) has the details.

| Protection                          | How                                                                                                                                       |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| A page can't act with your session  | Pages are served from a different site than the app, and the pages service has no session. The app's cookies never reach a page.          |
| A page can't reach its own origin   | CSP `sandbox` without `allow-same-origin` gives it an opaque origin, with no cookies or storage. The app's frame sets the same sandbox.   |
| A page can't send anything anywhere | `connect-src 'none'` and `form-action 'none'`, and scripts, styles, fonts and images only inline or from `/lib`.                          |
| Only the app can frame a page       | `frame-ancestors` lists only `APP_URL`'s origins.                                                                                         |
| A link opens one version, briefly   | The web app signs a link for one version, for 10 minutes, for a signed-in session only. `no-referrer` keeps the key out of other sites.   |
| The app trusts nothing a page says  | It reads one message from a page's frame, **Ask about this**, checks every field, and only prefills a question you then write and send.   |
| Checking a page reaches nothing     | The checker's browser runs as `desktop`, with no network and a throwaway profile, and reads only `.html` files in workspaces or `shared`. |

What a malicious page can still do:

- Show misleading content, inside the frame.
- Offer links to other sites, which open in a new tab or the phone's browser when you click them. Because of `allow-popups-to-escape-sandbox`, a site opened that way is an ordinary tab.
- Put words in a link's URL that a site you open learns, the same as any link you click.

The app's own session, your teammates, the computer and the vault are out of its reach.

## Known risks

These are open, with the planned mitigation for each.
They matter most when the computer runs in the cloud.

### 1. On Railway, the browser runs without its sandbox

Chromium's sandbox needs user namespaces, which Railway's container runtime refuses.
botd detects this at startup (`apps/botd/src/sandbox.ts`) and starts browsers with `--no-sandbox`, with a warning in its log.
Locally, Docker Compose runs the computer with `seccomp=unconfined`, and the sandbox stays on.

Without the sandbox, a renderer exploit runs as the `desktop` user, with access to every screen's browser profile and display, the shared folders, and the local services below.

**Mitigation:** run the computer on a host that allows user namespaces (a Firecracker-based host or a small VM with Docker), show the sandbox state in the app, and add a setting that refuses to start browsers without it.

### 2. VNC servers accept local connections without a password

Each screen runs `x11vnc -localhost -nopw`.
`-localhost` keeps it off the network, but any process in the container can connect, including the `bot` user's shell, which could take control of a screen and bypass the lease and the apply guard.

**Mitigation:** serve VNC over Unix sockets that only root can open, with botd bridging them, or give each server a random password only botd knows.

### 3. Codex app-server listens on localhost without authentication

`codex app-server --listen ws://127.0.0.1:4500` has no credential, and Codex runs with full access and no approvals of its own.
A process that reaches it, such as an unsandboxed browser exploit, could drive a teammate.

**Mitigation:** a Unix socket only root can open, a token on the listener, or a separate network namespace for Codex.

### 4. Egress is a browser setting, not a network rule

Browsers use the SOCKS proxy because of their flags.
A process that ignores them leaves from the computer's own address.

**Mitigation:** block outbound traffic for the `desktop` user except to the proxy (needs `CAP_NET_ADMIN`), or give browsers a network namespace whose only route is the proxy.

### 5. The browser updates only when the image is rebuilt

Chromium comes from Debian's packages at build time.

**Mitigation:** rebuild the image on a schedule and after Chromium security updates, and show the Chromium version in the app.

### 6. Teammates share a Linux user

Every screen's browser runs as `desktop`, and every teammate's shell as `bot`.
The lease and the apply guard are enforced by botd, not by the operating system, and memory scopes are a database boundary, not a file one.

**Mitigation:** a Linux user per screen, and longer term, a container or microVM per teammate.

### Suggested order

1. Move the computer to a host with user namespaces (risk 1, and it unblocks 4).
2. Put VNC and Codex behind root-only sockets or credentials (risks 2 and 3). These matter even with the sandbox on.
3. Show the sandbox state and browser version in the app, and rebuild on a schedule (risks 1 and 5).
4. Enforce egress at the network layer (risk 4).
5. Separate users, then machines (risk 6).

## Operational advice

- Generate `BETTER_AUTH_SECRET`, `WORKER_SECRET` and `BOTD_TOKEN` with `openssl rand -hex 32`, and `ENCRYPTION_KEY` with `openssl rand -base64 32`. Never deploy the development defaults.
- Keep Postgres and the computer private. Only the web app and the worker's websocket endpoints need public addresses.
- Back up Postgres, `ENCRYPTION_KEY`, and the computer's `/home` volume together.
- Rotate a webhook's URL if it leaks.
- Keep your Google OAuth client to yourself, and remove a Gmail, Calendar or Notion connection you no longer use: removing the last one on an account signs the app out of it.
